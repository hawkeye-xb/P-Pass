P-Pass 手机传照片给桌面这件事，中间有一步叫 `flow.fetch`：手机跟桌面说"我有一张照片要给你"，然后在同一次网络请求里死等，直到桌面把这张照片整个拉完、落盘、确认，才收到一句回音。

这个设计在同一个 Wi-Fi 下从来没露过馅。局域网延迟是毫秒级的，一张照片传完最多几秒，"等一下"感觉不出来。

它在跨网络、走中继（relay）的场景下会出一个很具体的问题：手机这边给这次等待设了 15 秒上限。传一张几百 KB 的截图，15 秒绰绰有余。传一个 224MB 的视频，走中继网络，光是这一次传输就可能要 80-90 秒。

于是手机会在第 15 秒准时判定"桌面没反应"，报错、退避重试，过一会儿再试一次。用户看见的就是：算完了，然后一直干等，最后传失败。

## 这不是"网络慢"，是设计上的自我矛盾

这个超时值同时要服务两个完全相反的目标：

- 如果桌面真的死了、断线了，我们希望**尽快**知道，好去重试或提醒用户；
- 如果传输是正常的，只是文件大、网络绕了远路，我们希望耐心等下去，不要在它明明进展正常的情况下把它判死。

一个数字不可能同时满足这两件事。调大它，正常的死连接判定要等更久；调小它，大文件必然被误杀。我们把这个数字往上往下都挪过，每次只是换一种错误去承受，从来没有真正解决。后来项目里立了条规矩：调数字是止血，不是终态方案。

## "提交"和"等结果"，不该是同一次请求

往回退一步看，手机想做的其实是两件独立的事。一件是告诉桌面我要传这个，另一件是知道传完没有。

这两件事被焊在了同一次 RPC 里，所以这次 RPC 的时长下限，被"传输本身要花多久"这个完全不可控的变量决定了。而"传输花多久"和"这次网络请求该不该超时"根本是两个维度的问题。

业界管这个形状叫 HTTP 的 202 模式：提交任务，拿句柄，回头拿句柄查状态。查状态这个动作永远很快，不管背后的任务跑了多久。这套模式在项目里不是第一次用，桌面端的事件订阅早就一半推送一半轮询。这次是把它搬到手机传照片这条路上。

## offer 立刻返回，status 负责查账

新的流程是三步。新的第一步不再叫 fetch，改叫 offer：只登记意图，不搬字节。

```
手机: flow.offer（登记这次传输意图）  → 桌面立刻回应，不等传输
桌面: 后台把传输任务 spawn 出去异步跑，终态写进账本
手机: 隔一段时间 flow.status（查账本）→ active / completed / cancelled / failed / not_found
```

`flow.status` 是一次很轻的查询，只读数据库和一个内存里的"任务是否还在跑"的标记，不碰真正搬字节的那条数据面连接。所以不管这次传输实际要跑多久，`status` 请求本身永远能在正常的控制类超时（还是那个 15 秒，但现在它只管这一次轻查询）内返回。

这里有一条原则贯穿了整个实现：**手机只认账本，不认回声**。一次 `status` 查询超时，不等于传输失败。它只说明这次网络往返没成功，桌面账本上写的是什么状态，才是真相。下一轮再查一次账，如果账本仍是 active，就继续等，绝不因为一次查询超时就重新发一遍 `offer`、跟桌面正在跑的传输互相打架。

```kotlin
// NativeFlowDeliveryPort.kt（示意）
// 一次 status round-trip 失败 ≠ 传输失败；
// 只有账本明确写着 failed/cancelled，才是终态。
fun flowStatusPollOutcome(reply: FlowStatusReply?, consecutiveTimeouts: Int): PollOutcome
```

暂停和取消也借着这次分清楚了。之前"挂断连接"一个动作兜三层含义：租约还在吗，任务还在跑吗，用户还要不要。现在意图变化直接写账本，观察就是去查一次账，没人再靠"这通电话还接没接着"去猜。暂停留下的字节继续受保护，恢复时接着传；取消就是真放弃，那些字节随后被垃圾回收。

## 证明它是真的解决了，不是"看起来好了"

daemon 侧加了个测试，在数据面拉取里注入一段远超控制超时的延迟，断言手机侧必须靠轮询走到确认态、拿到回执。这个测试在改动前是真红的。

更硬的一个反证：临时把"记录当前任务，好让 suspend 能找到它去中断"这一行代码删掉重跑测试，`suspend` 变成了一个什么都没做的空操作，传输在后台悄悄跑完，测试断言的"必须收到明确的中断结果"直接失败。恢复那一行，测试立刻回绿。这证明测试锁住的是真实机制，不是摆设。

真机那一轮更直接。三星手机，全新配对，一个 224MB 的视频加 23 张照片，走中继。视频在账本上从 active 走到 completed，跑了 80 多秒，全程一次失败都没有。搁在旧代码里，它活不过第 15 秒。

## 还没做完的事

新机制没有把所有问题一次性解决干净，这里如实列出来：

- daemon 如果在传输过程中崩溃重启，目前 `status` 只会报告"任务不在跑了"，还不会主动重新拉起这次交付。这是设计里明确要求、但还没实现的一块；
- 重复查询、重复拉取在最终确认态之后是否真的零重传字节，还差一个直接的断言测试；
- 一次拉取的最后一刻，如果用户正好在那个瞬间点了暂停或取消，两种时序谁赢。这条边界竞态还没补测试；
- 旧版本手机配新桌面、新版本手机配旧桌面，两个兼容方向目前靠不破坏旧协议字段做保底，还没有专门的兼容性回归用例。

这条超时线前前后后被调过好几轮，每轮都在两个错误之间摆钟。直到有人回头问这个数字到底在同时回答哪两个问题，才算找到出口。
