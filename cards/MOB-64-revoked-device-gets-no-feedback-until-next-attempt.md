# MOB-64 桌面移除设备后，手机端在下次尝试前毫无反馈（L2）

> ⬜ 状态：未开工
> 级别：**L2** · 阻塞：无

## 问题

2026-09-09 真机回归（三星）：验收人在桌面端点击「移除」把该手机从已配对
设备列表删除（`device.revoke`，daemon 侧 `device.revoked = 1`）。手机端
**没有任何反馈**——首页状态、连接指示灯全部维持原样，直到用户自己在手机
上点了「移除设备」主动断开，才真正结束这段连接。

验收人原话（拍板本卡范围）：「按道理来说，主动被客户端清理了连接，也就
是说这个连接失效了。我们如果能判断出来的话，是需要给出提示的。要么我们
可以给一个笼统的提示，就是『客户端出现了问题』；相应的提示就是：我们
移动端已经连不上客户端了。算是优化，并不是崩溃，就是没有任何的反馈提示。」

## 根因（源码核实）

- `crates/daemon/src/authz.rs`：`revoked_gets_nothing_not_even_hello`——
  吊销后的设备连 `hello` 都会被 `Deny { msg_key: ERR_NOT_PAIRED }` 拒绝，
  daemon 侧行为是对的、协议早已支持这个信号。
- `apps/android/app/.../BackupUiStateHolder.kt` 的 `pairingLost` 只在
  **配对纪元为空**（`needsEpochRepair`，旧版本/ARCH-06 之前遗留数据）时
  触发一次性自愈尝试，失败才置位 `_pairingLost.value = true`——这条路径
  只覆盖「纪元损坏」，不覆盖「纪元本身正常、但设备被吊销」。
- 手机没有任何**主动探测**「我是否还被信任」的路径；只有在用户真正发起
  一次业务操作（传输/`backup.begin`）时才会从 daemon 拿到 `ERR_NOT_PAIRED`
  拒绝——而当前那次拒绝目前很可能被当成普通传输失败处理，不会被识别为
  「已被移除」这个特定语义，更不会主动展示给用户。

## 期望行为（验收人拍板，本卡范围收窄到这一条）

不需要做主动心跳轮询或新协议——**下一次任何一条业务通道拿到
`ERR_NOT_PAIRED` 拒绝时**，手机端把它识别为「已被移除/连不上客户端」，
复用现有 `pairingLost` 红卡语义展示一条笼统提示（如「移动端已连不上
客户端」），不需要精确区分「被移除」还是其他吊销原因。

## 验收标准

- [ ] 找到手机侧收到 `ERR_NOT_PAIRED`（或等价拒绝）的现有处理点（Flow
      delivery 的 hello/backup.begin 失败路径），确认当前该错误码是否已经
      被丢弃在通用失败处理里，还是从未被识别过。
- [ ] 收到该拒绝码时置位 `_pairingLost`（复用既有红卡渲染，不新增 UI 状态）。
- [ ] JVM 单测：模拟业务调用返回 `ERR_NOT_PAIRED` → holder 的
      `pairingLost` 变为 true。
- [ ] 反证：把该识别去掉 → 上一条变红。
- [ ] 真机：桌面移除设备后，手机端**不需要用户自己操作**，下一次尝试
      传输/心跳时首页出现「连不上客户端」提示（不要求瞬时/主动轮询探测）。

## 范围

- 只准动：手机侧收到 daemon 拒绝码之后的识别与 `pairingLost` 置位逻辑
  （`BackupUiStateHolder`、Flow delivery 的错误处理）、对应 JVM 测试。
- 不准动：daemon 侧 `authz`/`revoke` 语义（已经是对的，不用改）；不新增
  主动轮询/心跳协议；不新增新的 UI 状态或文案分类（复用 `pairingLost`）。
