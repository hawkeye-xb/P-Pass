# MOB-46 相册选择计数虚高——选 3 个显示 7 个，选 4 个显示 8 个

> 🔵 状态：待验收人复核 · 当前节点：卡面要求“相册数”，但现有 UI 文案明确显示“将备份 N 张照片”，两处数据源均有意累计各相册照片数 · 下一步：提供原始截图/复现，或裁决此处应显示相册数还是照片数后重写验收标准
> 级别：L1 · 阻塞：等待原始复现证据或“相册数 / 照片数”产品口径裁决

## 问题

验收人 2026-08-27 真机反馈：「相册的计算重复了？选了 3 个，显示 7 个，
选择 4 个，显示 8 个。」

选相册页勾选的相册数与界面显示的已选数不一致：两次观察都是
**显示数 = 实际勾选数 + 4**。计数说谎会直接摧毁用户对「我到底选了哪
几个相册、到底会备份哪些照片」的信任（同类信任事故见 MOB-29「已备份
数字在两次备份之间说谎」）。

## 期望行为

界面任何一处显示「已选 N 个相册」时，N = 用户真实勾选的相册数。

## 验收标准

- [ ] 复现：全新安装/已有数据两种状态下，勾 N 个相册 → 显示 N（N=1,3,4 各验）
- [ ] 单测钉住计数来源：勾选集合 → 显示计数的换算必须是一一对应
- [ ] 反证：构造一个会产生 +4 偏差的输入（如计数路径混入了非勾选桶），
  修复前红、修复后绿
- [ ] 真机：选相册页、备份页等所有出现已选计数的位置全部核对一遍
  （不止修被点名那一处）

## 范围

- 只准动：`apps/android/app/src/main/java/com/hawkeyexb/ppass/` 内相册
  选择/范围存储/计数展示相关代码（`BucketScreen.kt`、
  `BackupScopeStore` 等，以实际读到的为准）
- 不准动：范围过滤的备份语义本身（哪个桶该传归 MOB-40 已定的规矩）

## 阻塞与依赖

当前卡面“选 N 个相册 → 显示 N”与当前资源文案冲突：

- `BucketScreen.kt` 的摘要使用 `bucket_summary`，en/zh 分别为“`%1$s photos will back up`”/
  “`将备份 %1$s 张`”，其 `sumOf { it.count }` 是照片数口径；
- onboarding 完成页的 `photoCount` 也使用同一照片数口径。

在没有原始 UI 截图或产品口径裁决前，把两处累计改成选中集合的 `size` 会显示
“将备份 3 张”，但实际可能备份 7 张，属于把正确的照片计数改成假话。暂停实施，
待验收人确认要修的是“相册数展示”还是另一个未定位的计数展示。

## 线索（不是结论，实施时先取证）

恒 +4 的形状像「计数路径里混进了 4 个固定项」——疑似系统伪相册
（相机/截屏/收藏/全部照片之类）或默认桶被计进了显示数。实施第一步：
读计数的数据来源，确认这 4 个是什么，再决定是过滤还是改口径。
