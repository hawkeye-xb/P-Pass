## 开跑前的事件：本地构建 → CI 构建的覆盖升级崩溃（#1237）

这台机器原先装的是本地构建的 `0.10.0-test.1167`（服务版，向导已走完）。覆盖安装 test.13 后，服务陷入崩溃循环：每 5 秒被 SCM 拉起一次，退出码 1067，4 分钟内 54 次。启动日志：

```
{"detail":"migration: migration 1 was previously applied but has been modified","error_key":null}
```

根因已经实测：sqlx 的迁移校验和按 `.sql` 原始字节计算，仓库没有 `.gitattributes`。GitHub Windows runner 的系统 gitconfig 是 `autocrlf=true`，所以 test.13 的 `daemon.exe` 里嵌的 `0001_init.sql` 是 CRLF；本地构建检出的是 LF。数据库里记的是 LF 版的校验和 `41BF24B6…`，与 test.13 的不一致。

影响：CI 包升级到 CI 包时换行一致，目前没事。但只要 CI 的检出配置变一次，已装用户升级后服务就起不来。修法：用 `.gitattributes` 把 `*.sql` 固定为 LF，再加门禁。

处理：保留现场取证后，卸载并清空 ProgramData、库目录、用户 AppData，全新安装 test.13（一次 UAC）。之后服务稳定运行，IPC 返回 `unconfigured:true`，然后开始本轮回归。

## 升级路径（G2）为什么不适用

- Windows 版还没有发布过，没有要保住数据的已装用户。按 2026-10-22 的口径（不考虑旧用户、不写迁移），修好的问题一律在全新安装上验证。
- 同一版本内的覆盖安装（W3）与卸载重装（W5）在 10-28 补测里都通过，安装器对主人、库、配对的保留已覆盖。

## 修复

四个问题在同一个修复批次里处理，test.14 上按全新安装复测（先清掉 ProgramData、库目录、用户 AppData 与上面那份绕行配置）。

| 卡 | 修法 | 单测 |
|---|---|---|
| #1239 | 点「确认断开」后立即清本地配对、回欢迎页；通知电脑改在应用级后台作用域里尽力发一次，不等结果。Android 与 iOS 同改 | 通知挂住时清理已完成、断开立即返回；只发一次；调用方取消不影响清理与通知。反证：改回先等通知即红 |
| #1238 | 平台层回答「daemon 配置在哪」「停止开关在哪」，壳读配置、库位置、停止记录全部经这一个入口；daemon 写完 `config.toml` 后只给这一个文件授本机用户只读（目录仍私有，内容无秘密）。服务形态的停止只认 `wanted-state`，不再另记一份 | 服务形态停服后不进向导、不自愈、不为更新拉起，点启动恢复；未配置照旧进向导；库位置从 daemon 配置目录读。反证：改回读壳的数据目录即红 |
| #1236 | `logs.export` 随应答带回 daemon 自己的 `daemon.log` / `daemon.log.1` 尾部，导出方在线时用这份、打包时统一脱敏；服务不在线时写明「日志在服务私有目录，只能由在线的服务交出」 | 服务交出的日志进包且脱敏；老版本应答回退本地读。反证：不用服务交出的那份即红 |
| #1237 | `.gitattributes` 固定 `*.sql eol=lf` | 编进程序的迁移脚本不含 CR。反证：把一个 `.sql` 转成 CRLF 即红 |
