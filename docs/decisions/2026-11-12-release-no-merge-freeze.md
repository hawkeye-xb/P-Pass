# 发版不冻结合入：删掉「main 前进就拒绝」的守卫

- 状态：已采纳
- 日期：2026-11-12
- 采纳：产品负责人 2026-11-12 拍板方案 A（删守卫，保留 tag 不可移动）
- 关联：#1648

## 背景

`release.yml` 的「Create draft release」步骤里有一段守卫（原 1318–1324 行）：正式版（`release=true`）比较 `HEAD_NOW`（main 当前头）与 `GITHUB_SHA`（触发时提交），不等就 `exit 1`，理由是「验证与构建可能不是同一份代码」。

这个理由已经不成立：`BUILD_REF: ${{ inputs.release && github.sha || inputs.tag }}`（第 87 行）在正式版固定用触发时的提交，且全部 17 处 `actions/checkout` 都显式 `ref: ${{ env.BUILD_REF }}`——验证、构建、上传都锚在同一个 SHA，main 前进改变不了本次构建的任何字节。守卫是引入 `BUILD_REF`（REL-13 / #716）之前的历史遗留。

实际后果：2026-11-10 两次正式版构建因此被拒（每次白等 20–40 分钟），并催生了「发版期间冻结一切合入」这条本不必要的纪律。

## 决定

删掉「main 前进就拒绝」这一段守卫；**保留**「tag 已存在且指向别的提交则拒绝」这一段（tag 不可移动是对的）。同步改掉 `docs/RELEASING.md` 里「发版期间不能合入」的说法。

## 理由

**本质要保证什么**：一次发版是「触发那一刻的代码快照」，构建与验证必须锚定同一份代码；发版不该反过来锁住 main 的合入。前者由 `BUILD_REF` 保证，后者不该靠一条过时的比较。

**标准做法**：CI 发版用固定 ref 检出（已做），tag 不可移动用单独的「已存在且指向别处就拒绝」判断（已做）。「main 是否前进」不在需要保证的集合里，删掉即可。

**偏离说明**：无。删除后「想含最新代码就重新触发一次」是快照语义的既有结论，不是新引入的风险。

## 后果

- 发版与合入并行，正式版触发后 main 继续合入不再让本次发版被拒。
- tag 不可移动的保证不变（第二段守卫保留）。
- 验收（照卡 #1648）：构造「触发后 main 前进」必须正常建 tag 与草稿；构造「tag 已存在且指向别的提交」必须仍然拒绝；两处都带反证。

## 备选

- **保留守卫但降级 `::warning::`**：发版不再被拒，但每次都多一条误导性噪音（说「验证与构建不一定是同一份代码」，实际是同一份）。不取。
