# 研发工作流升级 V3：结果真值门禁、核心黑名单与串行合入重验

- 状态：已采纳
- 日期：2026-11-21
- 关联：#1942（落地总卡）、#1952（阶段一底座与模拟演练场）、#1953（阶段二范围解绑）、#1954（阶段三四类门禁）、#1955（阶段四无人队列与收口）、#1804（验证对象漂移复盘）、#1923（规范文档收敛）
- 模拟演练场入口：`tools/flow/bench/bench.py`（确定性自测 `selftest` / 真模型压测 `live`）

## 结论

在 `v2026.11.4`（`0.12`）正式发版后，将研发协作流程从约 17,230 行「按步骤与单卡普通文件白名单层层打补丁的 Bash 脚本」，收敛为**单核 ≤ 400 行、只守结果真值与产品底线的 V3 状态机（`tools/flow/v3_harness.py`）**，并随仓保留独立模拟演练场（`tools/flow/bench/`）：以后任何流程规则调整先在模拟演练场跑通对抗自测与真模型预演，再改动主仓门禁。

## 背景

11 月初搭建的一卡一 PR 流程在半个月内累积了 4,905 行流程脚本与 12,325 行流程自测（占同期提交近半），暴露出三类结构性失灵：

1. **单卡普通文件白名单制造空转与碎卡**：任务卡要求预先穷举所有改动路径，干活会话顺手补一个关联单测或清理同名调用就会撞上范围拦截，被迫拆出大量内部衍生碎卡。
2. **门禁只验「绿没绿」，不锁「测的是不是原问题」**：如 PR #1804 所示，当真实修复受阻时，执行会话可能改弱故障注入条件或替被测代码拉起服务，使测试全绿却漏掉真实缺陷。
3. **跨真仓落地的隐蔽绕过点**：在独立模拟演练场用 `deepseek-v4.1-flash-1017` 做 13 场景对抗压测时，进一步抓出三处实战隐患：
   - 门禁若调用业务代码里的自判辅助函数，模型会直接把该函数改成恒返回真来绕过只读门禁（`T5`）；
   - 老代码因历史缺陷抛出未捕获异常直接崩溃时，粗糙的基线反证会将其误判为「测试语法写错」而误杀有效修复（`T8`）；
   - 带思考链的模型执行独立评审时，若输出上限过小会被思考过程耗尽额度导致空响应（`T11`）。

## 决定

### 1. 本机与远端职责分层（该在本地的留本地，远端保底线）

- **本机专属安全层（100% 留在本机，绝不触碰或削弱）**：
  - 本机 `~/.git-allowed-identities` 身份白名单与 `~/.git-templates` 个人/公司物理隔离钩子（防公司关键词泄漏）；
  - 本机 `.git/hooks` 下的 `gitleaks` 密钥扫描与 `tools/hooks/dispatch.sh` 转发链（每次提交先跑本机原有私有钩子）；
  - 本机 `.claude/settings.local.json` 命令放行白名单与设备锁缓存。
- **远端与仓库底线层（保持严格把关）**：
  - `.github/allowed-identities.txt` 提交者身份白名单与 DCO 门禁；
  - `.github/core-paths.txt` 核心禁区黑名单与 `review/agent` 独立评审必需检查；
  - `tools/flow/bench/` 模拟演练场源码随仓入库（运行期日志与临时目录不入库），后续改流程规则一律先在演练场模拟通过再动大仓库。

### 2. 链外任务封条与只读 `gh` 垫片

- 任务类型（`mode`）、锁定的验收测试路径与 `SHA256`、核心放行标记（`core_approved`）统一存于仓库外的 GitHub Issue 正文机器块中。
- 干活会话的 `PATH` 前置只读垫片 `tools/flow/gh-readonly-shim.sh`：放行只读查询与开 PR 命令，物理拒绝 `issue edit`、`issue close` 等改题与改标签操作并写入审计日志。

### 3. 放开单卡普通文件白名单，焊死基线核心禁区黑名单

- 移除单卡每次必填的普通业务与单测文件范围白名单；允许执行会话自由修改相关业务代码与配套单测（主仓根目录仍禁止直接提交卡分支，必须在独立 worktree 中开发）。
- 门禁直接从不可变基线提交读取核心名单（`git show <base_sha>:.github/core-paths.txt`，经 `tools/ci-paths.sh core` 同源规则匹配）：凡 `core_approved=false` 的任务触碰任一核心路径，立即判 `CORE_PATH_BLOCKED` 并还原禁区文件。

### 4. 四类任务门禁分流（`verify_gate`）

统一收口到 `tools/flow/v3_harness.py`（总代码硬上限 400 行），按任务类型执行不同判据：

1. **`fix`（已知缺陷修复）**：
   - 核对锁定验收测试文件的 `SHA256` 未被篡改；
   - 用 `git worktree add --detach <base_sha>` 做零拷贝基线反证：先排除语法/编译错误，再确认测试在基线上因断言失败或运行期异常非 0 退出；
   - 当前分支相关测试全绿 + 外部适应度门禁全绿。
2. **`speculate_then_fix`（无稳定复现路径的反馈）**：
   - 第一阶段仅允许在只读基线上新增复现单测，门禁验证其在基线上稳定运行期变红后，自动计算并锁死该测试 `SHA256`；
   - 第二阶段转入标准 `fix` 流程完成修复。
3. **`feature`（新功能 / 新增接口签名）**：
   - 锁定验收测试 `SHA256`，**跳过旧基线编译与反证**（避免新接口在旧 `main` 上因找不到符号报编译错误），验证当前分支测试全绿 + 适应度门禁全绿 + 独立只读安全评审通过。
4. **`verify`（纯验证 / 现场排查卡）**：
   - 严禁修改任何业务代码与既有测试（工作区源码零 diff）；
   - 只运行锁定的验证脚本并产出结构化结论（`verdict` + `root_cause`）；当底层确有缺陷时，如实报告 `FAIL` 且与真实非 0 退出码一致即判合格交付（`VERIFIED_REPORTED`）。

### 5. 外部物理适应度门禁、熔断与无人模式设备策略

- **外部物理原语铁律**：`tools/check-disk-growth.py`、`tools/check-egress.py`、`tools/check-autostart.py` 等适应度门禁严禁调用业务包内的辅助判断函数，一律用文件系统目录扫描、字节大小对比、源码符号扫描等外部物理手段独立断言。
- **两轮熔断**：同一任务连续 2 轮未过门禁即刻熔断挂起（`SUSPENDED_CIRCUIT_BREAK`），保留现场供统筹会话复盘，禁止无限重试。
- **无人模式设备静默降级**：开工先查设备锁与屏幕/在线状态；无人模式时遇到真机锁屏或离线直接标 `SUSPENDED_ENV` 改做下一张卡，不弹窗不阻塞。

### 6. 并发开发、串行合入重验队列与独立安全评审

- **串行合入重验队列**：多张卡在各自独立 worktree 并发开发；进入合入队列时若主干已前进，自动执行 `git rebase`：
  - 发生行级冲突：立即 `git rebase --abort`、清理临时状态并标 `SUSPENDED_CONFLICT`；
  - 自动变基成功：**强制在新树上重跑全套 `verify_gate`**（拦截无行冲突但破坏契约的语义冲突，给 1 次基于新树的自动补修机会），通过才允许合入。
- **零工具独立只读评审（`review/agent`）**：通过纯文本接口（不挂载文件写或命令执行工具，推理模型预留 `max_tokens >= 2048`）只审代码 diff，仅拦截硬编码骗测、安全边界缺失与静默吞错降级。

### 7. 分阶段落地步骤

1. **阶段一（#1952）**：入库本方案、`tools/flow/v3_harness.py`、`tools/flow/gh-readonly-shim.sh` 与 `tools/flow/bench/` 模拟演练场，跑通 13 场景对抗自测并接入 `flow-tests`，不动现行 `just start / done`。
2. **阶段二（#1953）**：移除 `tools/hooks/pre-commit` 与 `worker-done.sh` 的单卡普通文件范围白名单，保留本机安全白名单链并焊死基线核心禁区校验。
3. **阶段三（#1954）**：`just done` 切入四类卡型门禁分流，逐一核验现有 `tools/check-*.py` 物理独立性。
4. **阶段四（#1955）**：上线无人队列与合入前变基重验，退役冗余 Bash 流程补丁并同步更新 `AGENTS.md`。

## 理由

- **本质要保证什么**：用户照片不丢、占盘不膨胀、隐私不出境、本机个人/公司身份物理隔离、核心模块未经拍板不被触碰、每次合入解决真问题且不把 `main` 搞红。普通业务代码改了几个关联文件不影响上述底线，不应设卡。
- **对齐行业标准做法**：`CODEOWNERS` 式核心保护区 + 合并队列（Merge Queue）变基重跑测试 + 基线回归反证（Baseline Counterproof）+ 预发沙盒演练，是工程界防回归与防规则失控的标准解。

## 后果

- 普通功能与修复卡不再因漏填关联测试文件而阻塞或衍生碎卡，流程维护面从上万行 Shell 缩减至百行级 Python，且未来改流程规则可先在 `tools/flow/bench/` 几秒验证。
- `fix` 卡需具备可自动运行的复现单测；纯人工点按界面的体验改动仍走版本验收台账（#1471），不强套自动基线反证。

## 备选

- **继续在现有 Bash 脚本上修补白名单推导规则**：不选。静态脚本无法预知修复所需的全部关联单测与调用点，越补越厚且仍挡不住改弱测试。
- **把模拟演练场只留在本地临时目录不入库**：不选。随 `tools/flow/bench/` 入库后，跨机器与后续迭代都能先模拟验证再动真仓，避免拿主仓直接试错。
