# MOB-29 库里删掉的设备照片会被悄悄传回来；「已备份」在两次备份之间是谎话　级别 L1

> ⛔ 未实施。**方向已由用户 2026-08-21 定调，但有一处计数语义要拍板**（见文末）。

## 用户定调

> 「如果在客户端删除掉手机备份的某一部分内容（而非本机的相片），我们在客户端
> 挂一个常驻提示，提醒用户：如果你删除了某个设备里面的照片，请同时先在该设备
> 删除，要不然它会重复备份回来；或者禁止这个设备再往文件里备份，并给出用户提示。」

核心诉求：**用户在库里删掉的东西不该悄悄回来，而且要让用户知道该怎么做。**

## 两个互相纠缠的问题

### ① 删掉的会被传回来（用户报的）

存储端算「手机还缺什么」只看索引。库里删了 → 索引没了 → 下一轮 `manifest`
报「缺」→ 手机重传。用户的删除动作被静默撤销。

### ② 「已备份」在两次备份之间是谎话（我量出来的，同源）

实测（2026-08-21，用户三星 SM-S9210 + 本机库）：

```
手机说已备份:  188 张
库里真有    :    3 张
库里没有    :  185 张   ← 手机在撒谎
```

那 185 条的来源查清了：`confirmed.json` 的 `bucketOf` 显示 **186 条属于相机
相册 `-1739773001`**，是 **8/20 16 时那轮全量备份**留下的（存储端审计佐证：
`2026-08-20 16 时 ingest.new = 186`）。用户后来在 Finder 里删光（当时 WATCH-02
还没修），我随后清库重装。**手机从此一直显示那 186 张「已备份」，而世界上任何
地方都没有它们。**

纠正机制**存在且有效**——`calibrateIfReachable` → `existCheck`（把全部已确认
hash 发给存储端问「你还有吗」）→ `removeMissing`。我强制跑了一次备份 job，
`confirmed` **188 → 3，且 3 张全部真在库里**。

**缺陷是：校准只在备份开始时才跑。** 两次备份之间，不管存储端发生什么（用户
删照片、库被换掉、磁盘坏了、换台电脑），手机上那个大数字一动不动——而它是
用户判断「我的照片安不安全」的唯一依据。**用户不拍照就可能好几天不校准。**

**①和②是同一件事的两面**：校准一跑，那 185 张就从「已备份」变回「待备份」
——数字诚实了，代价是它们会被重传。用户要的是**既不撒谎、也不悄悄重传**。

## 我建议的改法：墓碑 + 常驻提示，**不**封禁设备

### A. 墓碑（真正解掉「传回来」）

库里移除一条资产时，如果它的 `src_device` 不是本机（= 它是某台设备备份上来的），
把它的 hash 记进一张**墓碑表**。`manifest` 计算 `missing` 时排除墓碑里的 hash
——语义从「我没有它」变成「我**故意**没有它，别再发了」。

现成的抓手：`Reconcile::remove_asset` 已经在写审计
`asset.removed_external`（带 `target_hash`），只是没记 `src_device`
——删行之前把它读出来即可。

⚠️ **必须有逃生口**：墓碑同时也会挡住「库真的丢了数据、需要从手机恢复」这条路。
所以要有一个明确的「从设备重新取回全部照片」动作，一按清空墓碑。
**不许把墓碑做成不可逆的。**

### B. 常驻提示（用户明确要的）

桌面端挂一条常驻提示（不是一次性 toast），大意：

> 你删掉了 N 张来自「三星 SM-S9210」的照片。它们不会再被传回来。
> 如果你也想在那台手机上删掉，请到手机相册里删——我们不会代你动手机上的原图。

关键是把**边界**说清楚：我们只管库，不动设备上的原图。

### C. 不建议封禁设备

用户提的第二个选项（禁止该设备再备份）代价太大：因为删了一张老照片就停掉
**所有新照片**的保护，是拿更大的风险换更小的整洁。而且会造出一个新的失败态
（「我的备份怎么停了」），比重传更难排查。

## 要拍板的一处：数字怎么说

墓碑落地后，「已备份」这个数该怎么算？

1. **只数库里真有的**（上例 = 3）。最诚实，但用户删了 185 张之后看到数字从
   188 掉到 3，会以为出事了 —— 需要配一句「另有 185 张已按你的要求删除」。
2. **数「已交代过的」= 库里有的 + 墓碑里的**（上例 = 188）。数字稳定，但
   「已备份 188」里有 185 张实际上并不存在，仍然是一句会误导的话。

我倾向 **1 + 那句补充说明**，因为这个数字唯一的用途就是回答「我的照片还在不在」。

## 验收要求

- 集成：库里删掉一条设备来源的资产 → 同一 hash 在后续 `manifest` 里**不再**
  出现在 `missing`；清空墓碑后**重新**出现
- 集成：删掉一条**本机来源**（用户自己放进 `originals/` 的）资产 → 不进墓碑
  （本机的东西没有"重传"这回事）
- 集成：手机侧「已备份」数字必须在**下一次校准**内与库对上，而不是等下一次真备份
- 反证：每条都要有
- 真机：复现本卡开头那组数字比对，改后必须是「库里没有 = 0」，且删掉的照片
  不再被传回来
