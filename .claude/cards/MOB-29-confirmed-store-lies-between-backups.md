# MOB-29 「已备份」在两次备份之间是谎话（实测 185 张虚构）　级别 L1

> ⛔ 未实施。**三条真机反馈里最严重的一条**——App 会告诉用户照片安全，
> 而存储端一张都没有。

## 实测证据（2026-08-21，用户三星 SM-S9210 + 本机库）

比对手机的「已确认备份」集合与存储端索引的真实内容：

```
手机 confirmed:  188
库里真有      :    3
库里没有      :  185   ← 手机在撒谎的张数
```

那 185 条的来源查清了：`confirmed.json` 的 `bucketOf` 显示 **186 条属于
相册 `-1739773001`**（不是用户当前选中的相册），是 **8/20 16 时那轮全量备份**
留下的（存储端审计：`2026-08-20 16 时 ingest.new = 186`）。用户后来在 Finder
里把它们全删了（当时 WATCH-02 还没修，索引也没减），我随后清库重装。

**手机从此一直显示那 186 张「已备份」，而世界上任何地方都没有它们。**

## 机制（受控实验证实，不是推测）

纠正机制存在且有效：`calibrateIfReachable` → `existCheck`（`backup.begin` +
`backup.manifest` 带全部已确认 hash）→ daemon 回 `missing` → `removeMissing`。

我强制跑了一次备份 job，`confirmed` **188 → 3，且 3 张全部真在库里**。

**所以缺陷不是「校准坏了」，是「校准只在备份开始时才跑」。** 两次备份之间，
不管存储端发生了什么（用户在 Finder 删照片、库被换掉、磁盘坏了、换了台电脑），
手机上那个大数字一动不动，而它是用户判断「我的照片安不安全」的唯一依据。

窗口有多长：自动备份靠 content trigger / 周期兜底，没有新照片就不跑。
**用户不拍照就可能好几天不校准。**

## 为什么这条最严重

产品的全部价值就是「照片安全」这个承诺。显示一个虚高的「已备份 N 张」，
比显示「不知道」坏得多——用户会**据此删掉手机上的原图**。

## 可能的改法（未定，需讨论）

- App 进前台就校准（`BackupUiStateHolder.init` 已有 `calibrateFromDaemon()`
  ——**查它为什么没兜住这次**：11:18 App 打开时应该就跑过一次）
- 存储端主动推：库里资产被移除时给配对设备发信号，手机收到就校准
- 显示口径改成带时效：「上次核对：3 分钟前」，核对超时就降级为「待核对」
  而不是继续报一个旧数字

## 验收要求

- 集成：库里删掉 N 张 → 手机侧「已备份」必须在**下一次前台/下一次校准**内减掉
  N，而不是等下一次真备份
- 反证：把校准去掉 → 上面那条必须变红
- 真机：复现本卡开头那组数字比对，改后必须是 `库里没有 = 0`
