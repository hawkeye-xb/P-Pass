# 本地真机验证（E3）：`just verify`

交卡前一条命令在真机上跑冒烟和本卡的验收场景，判定全部交给脚本，人和 agent 只读最后一行。

## 怎么跑

| 命令 | 什么时候 | 跑什么 |
|---|---|---|
| `just verify <issue号>` | worker 交卡前（V1） | 改动涉及的端的冒烟 + issue「验收场景」段点名的场景 |
| `just verify --smoke android` / `--smoke mac` | 只想看某端还活着 | 该端冒烟 |
| `just verify --all` | owner 合批前（V2） | 场景库全部 |

- 涉及哪几端由改动路径决定（`tools/ci-paths.sh hit`，Android 的路径与 `ci-android.yml` 同源）。改动不落在任何端上时输出
  `VERIFY N/A`，只需 `just ci`。判定异常时按「涉及」处理（多跑一次，不漏跑）。基准是 `merge-base(HEAD, origin/main)`，
  所以先提交再跑。
- 自动做的事：编候选构建（daemon、testclient、debug APK；重编经 `tools/heavy-lock` 排队，可重入）、
  编或复用「上一版」基线 APK（按 sha 缓存）、拿设备锁、装包、配对、判定、收尾。
- 选项：`--counter` 所有场景都跑反证；`--no-build` 用现有产物；`--base <rev>` 换「上一版」（升级冒烟的基线、
  改动判定的基准）。基线 APK 在临时 worktree 里编，按 sha 缓存在 `~/.cache/ppass-e3/base/`。
- 单个场景：`tools/e3/run [--counter] <端>/<名字>…`；清单：`tools/e3/run list`。

第一次在一台机器上用，要先写本机配置 `~/.config/ppass/e3.env`（不进 git；各项含义见 `tools/e3/lib/adb.sh` 文件头，
本机的值记在 `local-state.md`）。缺项时脚本会报出缺哪个。

## 怎么读结果

最后一行就是结论：

```text
VERIFY PASS 1234 android 1/1 · mac 3/3  evidence/1234/20261102-120000
```

- 每个场景一行 `PASS|FAIL|SKIP <场景>`。`SKIP` 表示本机条件不具备，原因写在同一行，**不算通过**。
- 有没覆盖到的项时结论写 `PASS（不完整）`，并在「未覆盖」里列出：SKIP 的场景，以及只验了本机已装版本、
  没验候选构建的场景（例如 `mac/svc=已装版`）。交卡时照实写，不能写成全部通过。
- 失败时同一行下面列出前几条失败的判据。要看细节再打开证据目录：
  `evidence/<对象>/<时间>/<场景>/` 下有 `run.log`（过程）、`judge-main.txt` / `judge-counter.txt`（逐条判据）、
  `main/` 与 `counter/`（原始输出：日志切片、IPC json、dumpsys、界面文字；截图只作存档）。
- 交卡时把最后一行和失败场景的 `judge-main.txt` 贴进 issue，标 E3。

## 场景库

场景放在 `tools/e3/scenarios/<端>/<名字>.sh`，id 写作 `<端>/<名字>`，issue 的「验收场景」段直接写 id。

| 场景 | 内容 | 反证 |
|---|---|---|
| `android/smoke-upgrade` | 冒烟：上一版 debug 包配对桩、备份 N 张 → 覆盖装候选包：配对仍在、不崩、备份范围只含测试相册、桩与手机账本计数一致、无 FATAL | 升级后 `pm clear` |
| `android/onboarding-gate` | #1321：全新安装配对 → 决定页；杀进程仍回决定页；主按钮被拒 → 系统选图、取消回决定页；次入口选一张 → `marked onboarded via=pick`；清数据重配、全部允许 → 选范围 → `via=scope`；断开后连回同一台不再出决定页 | 无（真机只验正向；判据反证在 JVM 单测 `OnboardingGateTest`） |
| `android/p1-thumb-notjpeg` | 桩回非 JPEG 缩略图：手机拒收、「无法显示预览」、不崩 | 还原缩略图 |
| `android/p2-thumb-toolarge` | 桩回 4000×3000 缩略图：拒收、内存增量 < 100MB | 还原缩略图 |
| `android/p3-video-lazy` | 视频页浏览不下载、点播放才下（量桩进程上行字节） | 浏览时点播放 |
| `android/p4-video-noroom` | 手机空间不够时点播放：提示空间不足、不下载、不崩（声明大小注入成 1TB，不占满手机） | 改回声明大小 |
| `android/p5-video-declared` | 视频实际大于声明：中止、提示失败、不播放 | 改回声明大小 |
| `mac/svc` | 冒烟：已装服务在线；停服务 60s 不被拉起；强杀 30s 内自恢复 | 停服务期间拉起 |
| `mac/svc-open` | 服务停着时打开窗口（先 bootout、5s 后开窗口）：60s 内不被拉起，desktop.log 落在 `stopped outside` 后不回 running（#1300） | 开窗口后第 10s 拉起 |
| `mac/eph-backup` | 冒烟：候选 daemon 桩与 testclient 配对、备份，计数一致、无 panic | 删桩里一条资产 |
| `mac/pkg` | 桌面包编解码库合规 | 塞入禁用库 |
| `mac/upgrade` | 冒烟：清成空白数据（原件保留）→ 上一版 release 收编原件作基线 → 覆盖装候选签名包：NodeId、已配对设备、照片数不变，服务就绪、无 panic；结束装回开始前的版本与数据 | 不清空白、在本机库上装上一版 |

Android 场景的素材只推进专用测试相册 `Pictures/00-PPassE3/`（`E3_ANDROID_ALBUM` 可改名），配对时备份范围只勾它、
不勾相机相册，存下之后经 `run-as` 读回 App 的范围核对，不是只有测试相册就判失败（#1412）。所以测试机相机相册里有当天
拍的照片也不影响计数；`ensure_paired` 复用旧配对前同样核对范围，不符就重新配对。相册名以 `00-` 开头，选范围页按名字
排序时排在首屏；首屏找不到它时配对直接报错，不盲点。

Windows、iOS 只有接口说明（`tools/e3/scenarios/win/README.md`、`ios/README.md`）。

Mac 只有一个安装槽（`docs/decisions/2026-11-02-one-install-per-test-device.md`）：拿到 mac 设备锁就可以覆盖。
`just verify` 涉及 Mac 时先编开发版签名包（与 `just dev mac` 同一份构建；V2 / test 回归可用 `E3_MAC_CAND_APP` 指向 CI 出的
正式签名包），`mac/upgrade` 把它装上，
`mac/svc`、`mac/eph-backup` 接着在候选上跑，全部跑完再装回开始前的版本（`RESTORE mac → <版本>` 一行）。
已装 daemon 的 IPC 是签名 socket，脚本连不上：判定用 launchctl、进程表、它的日志，以及它自己的 `diag export`
子命令导出的 status 与设备表（只读）。身份与配对在钥匙串里、全机一份，场景不换库目录、不写库。
服务开始时是停着的（按用户停的处理）就 SKIP，不替用户拉起。配对桩是 `daemon --ephemeral`：内存身份、临时沙盒，
所有注入只改桩自己的沙盒。

## 怎么写场景

一个场景是一个 bash 文件，由 `tools/e3/run` 在子 shell 里 source。共享库按端自动加载（`lib/common.sh`
总在，Android 加 `adb.sh` `eph.sh` `android-flow.sh`，macOS 加 `eph.sh` `mac.sh`）。

```bash
DESC="一句话：验什么"          # tools/e3/run list 显示
COUNTER=on                     # 注入类必须 on；其余 off（--counter 时也跑）

setup()   { … }    # 准备：装包、配对、造素材。返回 77 = 本机条件不具备（记 SKIP，原因写最后一行输出）
act()     { … }    # 操作，并把判定要读的原始输出全部写进 "$OUT"
judge()   { … }    # 只读 "$1" 目录判定：每条用 check 记 ok/FAIL，最后 verdict
counter() { … }    # 去掉（或加上）故障条件，同样把原始输出写进 "$OUT"；judge 必须判红
teardown(){ … }    # 收尾，总会执行（还原注入、删推过的素材）
```

规矩：

1. **judge 是纯函数**：只读证据目录，不碰设备、不看截图。这样 `tools/e3/run judge <场景> <目录>` 可以离线重放，
   反证也只是「换一个目录再判一次」。
2. **成功路径也要有日志行可判**。判据写成「日志里出现哪一行算通过」，找不到证据 = 失败。
3. **注入类必须有反证**，且反证要让 judge 的关键判据变红，不能只是让某个无关项失败。
4. 只在 P-Pass 在前台时点（`tap_text` / `fg_guard`），手机上还装着别的 App。造素材用程序生成（`gen_photos`），
   推进相册后要发媒体扫描广播（`push_photos` 已做）。
5. 不进仓库：本机路径、设备序列号、主机名（写 `e3.env`），以及安全攻防细节。
6. 新冒烟场景登记到 `tools/e3/verify` 的 `SMOKE_<端>`。

判定小工具（`lib/common.sh`）：`check <描述> <命令>`、`has_line` / `no_line <文件> <正则>`、`count_lines`、
`eq_file <文件> <值>`、`num <文件> <op> <值>`、`jget <json 文件> <表达式>`。

## 研发本地看改动（macOS）

```bash
just dev mac
```

编开发版（debug daemon 组装成签名 helper + `tauri bundle --debug` 的外壳，团队 Developer ID 与 daemon 描述文件签名，
不起 `tauri dev`），取 mac 设备锁后覆盖 `~/Applications/P-Pass.app`、等服务就绪。覆盖前装的是正式签名包时留一份快照。
看完装回：

```bash
just restore mac --snapshot
```

或装回某个 release：`just restore mac v0.10.3-test.2`。只想编、不装：`tools/e3/dev mac --build-only`。
描述文件第一次用要给 `PPF_DAEMON_PROVISIONPROFILE=<daemon 授权文件>`（之后读 `just mac-dev` 记下的那份）。
只改界面时 `just mac-dev`（tauri dev 热更新）更快；`just dev mac` 是装成完整 App、和用户拿到的形态一致。

## 研发本地看改动（手机）

```bash
just dev android [页面] [--fresh]
just dev ios [页面] [--fresh]
```

增量编 debug 包（Rust 走共享缓存，见下节）→ 取设备锁 → 覆盖安装（不卸载，数据保留）→ 打开 App。设备被别的会话占着
（`just dev`、`just verify` 正在用）就直接拒绝并打印占用者，不排队。iOS 的页面就是 `PPASS_ROUTE`（取值见
`apps/ios/PPass/App/RootView.swift`，只 DEBUG 包读）；安卓还没有深链，给了页面只提示、先启动 App。`--fresh` 先卸载再装
（清数据，从头走流程时用；装着签名不同的包时覆盖装会失败，也要 `--fresh`）。设备按在线探测选：只有一台就用它，多台时用
`E3_ANDROID_SERIAL` / `PPASS_DEVICE` 指定。结尾打印「用时 Ns」。

## 共享编译缓存

主副本与所有卡目录共用一份 Rust `CARGO_TARGET_DIR` 与 Xcode DerivedData（主副本旁的 `P-Pass-cache/`），卡目录只放源码。
配置在主副本旁的 `.env.ppass-dev`：`just start` 自动建，`tools/e3/dev cache` 手动建或查看；justfile 的 `dotenv-load` 从当前目录
往上找到它，所以 `just` 命令自动带上，CI 与没有这个文件的机器不受影响。直接跑 `cargo`（不经 `just`）不读它，先
`set -a; . ../.env.ppass-dev; set +a`（路径以 `just start` 打印的为准）。Gradle 依赖缓存本来就在 `~/.gradle`，`just dev android`
另开 `--build-cache`。

共享之后：第三方依赖只编一次；本仓的 crate 在不同卡目录路径不同，仍各编一份（增量）。`target/debug/daemon` 这类最终产物
各目录共用、后编的覆盖先编的，所以「编完再用」的脚本要在 `tools/heavy-lock` 里编完立刻拷走（`just dev ios` 就是这样做的）。
重编互斥仍由 `tools/heavy-lock` 管。

## 装回原版本

`just restore mac <tag>`（`tools/e3/restore`）：先取 mac 设备锁，从 GitHub Release 下载该 tag 的 macOS 包，校验 SHA256 与团队签名，
覆盖安装并核对已装与 daemon 的版本号。`just restore mac --snapshot`：装回 `just dev mac` 覆盖前或 `mac/upgrade` 开始前留的那一份
（装的可能是不在 Release 上的开发构建）。其它端待收编。

数据快照（#1311）：候选可能带新的数据库迁移，装上就改了库，旧版 daemon 不认新迁移会拒绝启动。所以留快照之后的第一次
安装会在服务停下后，把 daemon 数据（`~/Library/Application Support/P-Pass` 下的 `config.toml`、`libraries/`，以及库目录下的
`.ppf/`）存进快照；`--snapshot` 装回时先把这份数据放回去再起服务。不含照片原件和日志：候选期间新备份进来的照片，原件留在库里，
索引随快照回退。装回后要求 daemon 就绪、版本对、`diag export` 读得出照片数，否则失败。快照里没有数据（旧快照）时只装回程序，
旧版起不来照样判失败。`just restore mac <tag>` 不带数据：从更新的库装回旧 tag 会起不来。
`mac/upgrade` 不依赖本机库的现状：留快照后先把数据清成空白（删 `libraries/` 与 `.ppf/` 里除 `library-id` 外的内容，原件、
`config.toml` 保留），上一版启动时把原件收编进新索引作为基线，收尾再恢复快照。

## 设备锁

`tools/e3/lock [--no-wait] <mac|android|win|ios> <命令…>`：同一台设备同一时间只给一个会话用，后来的排队等（`/usr/bin/lockf`，
进程退出即释放）；`--no-wait` 被占就打印占用者并退出 75（`just dev` 手机用它）。`tools/e3/run` 自动拿锁，手动操作设备时也套一层。

- **只在操作设备时持锁**：构建在锁外，装包、启动、点界面、取证在锁内。本机的 P-Pass 桌面 App（含正式版）也算 mac 设备：
  替换、安装、重启、停掉它的函数（`svc_stop`、`svc_start`、`mac_quit_shell`、`mac_install_app`、`mac_data_restore`、
  `mac_data_blank`）没持 mac 锁就拒绝执行（`tools/e3/lib/mac.sh` 的 `mac_need_lock`）。
- **占用记录只代表活着的持有者**：持锁命令退出（含被杀）就删掉 `.who`；`status` 发现记录里的进程已退出时显示
  「空闲（残留记录指向已退出的进程 <pid>）」并清掉残留。
- **人工验收持锁**：人照 SOP 验收前，owner 先替他拿住涉及的设备，验收结束再放；期间 agent 的场景排队等，`--no-wait` 退出 75，
  `status` 显示「人工验收中（自 <时间>）」。持锁进程意外退出时锁自动释放。

  ```bash
  tools/e3/lock hold-for-human mac ios      # 一次可拿多台；前面有场景在跑就排队，最多等 E3_HOLD_WAIT 秒（默认 600）
  tools/e3/lock release-human mac ios       # 验收结束
  ```

  和 `claim` / `release`（设备主人）的区别：`claim` 记归属、不持锁，别人取锁直接被拒；`hold-for-human` 真持锁，别人排队，
  放了就接着跑。
