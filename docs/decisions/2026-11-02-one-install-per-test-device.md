# 每台测试设备只有一个安装槽

- 状态：提议
- 日期：2026-11-02
- 取代：本 ADR 的前一稿《开发版与正式版同机并存》（双身份方案，已否决，见「备选」）

## 结论

1. **一台测试设备同一时间只装一份 P-Pass。** 开发版与 test 包、正式包轮流装进同一个位置，
   不做「开发版」这个第二身份。
2. **冲突靠排队解决，不靠隔离。** 谁要用某台设备，先取这台设备的锁（`tools/e3/lock`，另一会话的
   场景库卡在做），用完释放。开发者交卡前的真机验证与产品负责人的 test 回归，经由同一把锁排队。
3. **不需要新的 Apple 资源**：沿用现有团队签名与 daemon 描述文件；#1115 的签名校验一字不改。

## 背景

这件事本质上要保证两点：开发者（含 agent）交卡前能在真机上验证自己的改动；这种验证不能打乱
产品负责人正在进行的 test 回归。

现状：`just mac-dev` 与正式包共用 `~/Applications/P-Pass.app`、LaunchAgent、数据目录。正式包在时
它直接拒绝（`tools/mac-dev.sh` 的 `refuse_release`），开发者只能自己动手退出、移走正式版。
11-02 的 test.2 回归把主 Mac 上的 P-Pass 换成了 test.2，照片库也被搬走了。问题出在「谁在用
这台设备」没有记录、没有排队，而不在于两份安装不能共存。

Mac、Windows 回归机、三星、iPhone 都是专用测试机，不存在「在同一台机器上跑生产」的需求。

## 决定

- **设备锁**：每台设备一把锁，记录持有人、用途、被测版本和取锁时间。实现由场景库卡负责
  （`tools/e3/lock`），本 ADR 只规定使用规则：
  - 装、卸、覆盖安装、跑回归之前必须先持锁；
  - 被别人持有时排队等待，不抢占、不强拆；
  - 用完必须释放。持有人消失时的处理规则由锁的实现卡给出。
- **`just dev <端>`**：先取锁，构建开发版，**直接覆盖**已装版本。测试机上允许覆盖，`mac-dev`
  里「正式包在就拒绝」的闸门改成「先取锁再覆盖」。
- **`just restore <端> <tag>`**：先取锁，从 GitHub Release 下载指定的 test 包或正式包，装回去，
  并核对装上的版本号与签名。
- **回归开始前**：QA（产品负责人或代跑的 agent）先取锁，再把设备 `restore` 到被测 tag；
  回归期间这把锁一直由 QA 持有。
- 各端「覆盖」的含义：

| 端 | 覆盖方式 | 数据 |
|---|---|---|
| macOS | 覆盖 `~/Applications/P-Pass.app`，按现有 LaunchAgent 换进程 | 数据目录保留 |
| Windows | 运行本地构建的 NSIS 安装包，覆盖安装 | 数据目录保留 |
| Android | debug 与 release 签名不同，不能直接覆盖，要先卸载再装 | 卸载时清空（测试机可接受） |
| iOS | Xcode 装的开发构建与 TestFlight 包 bundle id 相同，直接替换 | 由系统决定，以实测为准 |

## 理由

- **对齐的标准做法**：共享测试设备的通行管理方式就是「设备预约 / 锁 + 安装指定构建」，如设备农场
  或真机实验室的 checkout 机制。问题的根源是资源争用，用排队直接解决资源争用即可。
- 保持单一身份，正式版的签名、协议、更新链都不用动，「正式版行为零变化」天然成立。
- 只有在需要验正式签名链路时，才单独打正式签名包（沿用 `just verify-m1`）。

## 后果

- 同一台设备不能一边开发一边验收，两件事要排队。验收优先级的设定由锁的实现卡负责。
- 开发者每次用完都要 `restore` 回原来的版本或释放锁，否则下一位拿到的设备处于未知状态。
  `restore` 要做到能一条命令执行完。
- 外部协作者没有团队证书，仍然跑不起桌面端。这个问题不在本 ADR 范围内，需要时另行决策。

## 实施（另开卡，本 ADR 不实现）

1. `tools/e3/lock`：设备锁（场景库会话在做）。
2. `just dev <端>`：先 macOS（改 `tools/mac-dev.sh` 的闸门），再 Android、iOS、Windows。
3. `just restore <端> <tag>`：下载、安装、核对版本与签名。
4. 回归 SOP 里加上「取锁 → restore → 回归 → 释放」这一步。

验收要求：同一台设备上，A 持锁时 B 的 `just dev` 会排队等待；A 释放后 B 能覆盖安装；
`just restore` 能装回指定 tag，且版本号核对通过。

## 备选（未采纳）

- **双身份并存**（本 ADR 前一稿：开发版独立 bundle id / 服务名 / ALPN / 签名路径）。否决理由：
  - 产品负责人的判断是，一台机器同时只能有一个 daemon 占用 iroh 网络（与 Tailscale 等同类工具
    不能共用同一个道理），两份 daemon 并存本身就站不住。
  - 要改协议、签名校验和打包，还要新建 Apple 资源，代价远大于收益。
  - 测试机没有「同机跑生产」的需求，并存要解决的问题并不存在。
- **维持现状**（`mac-dev` 遇正式包就拒绝，由人手动移走）：没有记录谁在用设备，test.2 那次的事故
  还会再发生。
