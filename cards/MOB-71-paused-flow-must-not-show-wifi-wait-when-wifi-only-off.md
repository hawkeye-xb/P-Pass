# MOB-71 关闭「需要 Wi‑Fi」后暂停不得再显示 Wi‑Fi 等待（L1）

> 🟡 状态：代码完成，待三星真机验收
> 级别：L1 · 阻塞：无

## 问题

2026-09-11 真机回归：手机只连蜂窝网络，初始「需要 Wi‑Fi」开启时，选择 3 张照片后显示「将在连接 Wi‑Fi 后进行」，符合预期。用户关闭该开关后，当前轮立即开始在蜂窝网络上传，也符合预期。

第一张完成后用户点「暂停」，首页却再次显示「将在连接 Wi‑Fi 后进行」。此时持久设置仍是「需要 Wi‑Fi」关闭；暂停只是用户暂停当前 Flow 轮次，不能重新制造一个已被关闭的网络条件。该文案误导用户以为必须重新连接 Wi‑Fi 才能继续。

## 期望行为

「将在连接 Wi‑Fi 后进行」只表示**当前启用 Wi‑Fi 限制且网络不满足**。当 Wi‑Fi 限制已关闭时，任何 Flow 生命周期转换（开始、暂停、继续、取消或失败）都不得显示该文案；暂停态只呈现暂停/继续的真实状态。

## 验收标准

- [ ] 自动化：Wi‑Fi 限制开启且网络受限时，投影为 Wi‑Fi 等待；关闭限制后，重新计算为非 Wi‑Fi 等待。
- [ ] 自动化：在上述关闭限制后的运行中插入暂停、继续、取消和失败状态转换，Wi‑Fi 等待投影始终不复活。
- [ ] 反证：把等待文案的判据改回只读旧的/锁存的网络状态，焦点用例必须失败。
- [ ] 真机：蜂窝网络下「选择照片 → 关闭需要 Wi‑Fi → 开始传输 → 暂停」后，首页不显示 Wi‑Fi 等待；点继续后仍可在蜂窝网络继续。

## 范围

- 只准动：Android 端 Wi‑Fi 等待状态的来源与投影（`MainActivity.kt`、直接相关的备份 UI 状态/测试）。
- 不准动：Wi‑Fi 限制的产品默认值、关闭确认、WorkManager 调度策略、Flow 暂停/取消账本语义、relay 策略。

## 当前节点

根因已确认：`wifiDeferred` 是触发时的瞬态标记；关闭 Wi-Fi 限制原先只持久化设置，
传输中的 `busy` 暂时遮住旧提示，暂停后却重新显示。现在渲染同时要求当前 `wifiOnly`
仍开启，开关变更也即时重算/清除该标记。
