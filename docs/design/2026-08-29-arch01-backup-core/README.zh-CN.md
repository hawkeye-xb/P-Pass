## 已定业务原则

```text
一条核心处理管道
+ 一本长期有效的手机本地逻辑账本
= 前台、后台唤醒、触发器与传输都遵守同一份事实。
```

- **待传列表不物化。** MediaStore 本身就是「还有哪些照片」的事实源；手机不保存它的缓存。循环每传完一张，就向 MediaStore 取下一张。没有分页窗口，没有发现水位，没有待传快照。
- **凡是对某张照片做过决定，就必须有这张照片自己的 order 作为证据。** 每张照片的结局都落在 order 上：`CONFIRMED` / `FAILED` / `SKIPPED_BY_USER` / `SKIPPED_SOURCE_MISSING` / `CANCELLED_BY_SCOPE`。不用区间记录或游标位置代替逐张证据。
- **照片的身份是内容 hash（BLAKE3）。** `(_id, 版本)` 只是快速过滤用的索引；`_id` 变了但 hash 没变，就是同一张照片，不重新传。
- 用户 `Pause` 是长期命令：杀 App、重启、网络恢复和后台唤醒均不能解除；只有 `Continue` 可解除。任何触发都先检查暂停。
- Wi‑Fi、电量、今天额度或 Desktop 不可达属于条件等待：释放 FGS，登记对应的唤醒，条件恢复时自动继续，不消耗失败预算。
- 触发器只表达「可能有新照片」；循环运行期间再来的触发合并。严格一张一张处理，按 generation 升序，新照片不插队。
- 一张照片只有在 Desktop **完整接收、验证、可靠保存，并明确确认本地拥有**后才是 `CONFIRMED`。
- 一旦 `CONFIRMED`，随后改范围、取消或手机重启都不能否定该完成事实。
- P-Pass 是单向备份，从不删除手机原图。对账发现 Desktop 上缺失已确认的照片时**自动补传**；只有带着用户明确决定的 order（`SKIPPED_BY_USER`）不补传。

## 逻辑账本

下列是逻辑事实分类，不规定表结构。唯一的存储前提：order 必须能按行、按事务写入（SQLite）。整份快照每次整体重写的存储，写入代价随条目数增长，会逼出分页窗口；按行事务写入时，一次写 5000 条 order 也只是一个事务，不需要任何窗口。

| 类别 | 保存的事实 | 生命周期 |
|---|---|---|
| 用户配置与范围 | 自动备份开关、Wi‑Fi/电量条件、已选相册 | 换 Desktop 后保留 |
| 用户控制 | `PAUSED_BY_USER` | 仅 Continue 改变 |
| order 表 | 每张照片一行：`(_id, 版本) → BLAKE3 内容 hash` 与状态；状态是未完成（可续传）或五种结局之一 | 当前配对的备份历史（见「换 Desktop」） |
| 快路径提示 G | 最近一次处理到的 `GENERATION_MODIFIED`；只是加速提示，丢失或偏差不丢照片 | 可随时丢弃，下一次慢路径兜底 |
| MediaStore 版本 | 上次对账时的 `MediaStore.getVersion()`；一变就触发全量对账 | 手机本地 |
| FGS 受阻事实 | FGS 被拒或超时；App 进入前台前不再调用 `startForegroundService`（#414） | App 进入前台时清除 |
| 当前配对与传输归属 | 当前 Desktop、有效传输归属与 partial 所属关系 | 换 Desktop 时清理 |

order 的五种结局：

| 结局 | 含义 | 慢对账是否会自动重新传 |
|---|---|---|
| `CONFIRMED` | Desktop 已完整接收、验证、可靠保存并确认 | Desktop 上缺失时自动补传 |
| `FAILED` | 单张失败，立即重试 1 次后仍失败 | 每次慢路径重试一次 |
| `SKIPPED_BY_USER` | 用户「取消剩余 N 张」时逐张写入 | 不会 |
| `SKIPPED_SOURCE_MISSING` | 手机原文件已不存在 | 不会（没有源可传） |
| `CANCELLED_BY_SCOPE` | 恢复时发现这张已移出范围 | 待定：相册重新纳入范围后是否重新准入 |

### 不变量

```text
一张照片被做过任何决定
= order 表里有这张照片自己的一行，写明结局。

确认与记账
= 处理 Desktop 完成凭据时，order 置为 CONFIRMED、(_id, 版本) → hash 映射、G 的推进
  在同一次写入中完成；不会出现只落了一半的账。
  崩溃若发生在 Desktop 确认之后、这次写入之前，重启后这张会再传一次；
  Desktop 按内容去重，结果幂等。

Desktop 完成凭据
= 已完成事实；后续控制操作不能覆盖它。

同一 BLAKE3 hash
= 同一张照片；_id 或版本变化只更新映射，不重新传。

批量结局（取消剩余 N 张）
= 一个事务写入 N 行；要么全部生效，要么全部不生效。
```

## 发现

### 快路径

- 查询 `GENERATION_MODIFIED > G`，按 generation 升序取。G 只是加速提示：快路径漏掉的照片不会丢，下一次慢路径会补上。
- 内容触发批量带上变化的 URI；循环传完一张取下一张时也走快路径。所以循环期间新拍的照片会被自然接上，期间再来的触发合并进当前循环。
- **待定：** `GENERATION_MODIFIED` 只在 API 30+ 存在，App 的 minSdk 是 26。API 26–29 上快路径用什么键、会不会漏照片（漏的能否全靠慢路径兜住）尚未定。

### 慢路径

触发：每 5 小时兜底、App 打开、`MediaStore.getVersion()` 变化（变化时做全量对账）。

1. **归并比对：** MediaStore 与 order 表都按 `_id` 排序，逐行归并，只读 `_id`、修改时间、大小三列。
2. **hash 映射：** 对新增或版本有变化的照片算 BLAKE3。
   - hash 已存在：MediaStore 重建或文件被移动，只更新 `(_id, 版本) → hash` 映射，不重新传。
   - hash 是新的：进入传输（编辑过的照片就是新版本，按新版本传）。
3. **源缺失：** order 表里有、MediaStore 里没有的，记为 `SKIPPED_SOURCE_MISSING`。**待定：** 这一步是否作用于 `CONFIRMED` 的 order——若作用，用户删掉已备份的原图就会覆盖完成事实，与「CONFIRMED 不可否定」冲突。
4. **桌面存在性：** 分页询问 Desktop，已确认的照片是否都还在。缺失的**自动补传**；`SKIPPED_BY_USER` 等带着用户明确决定的 order 不补传。**待定：** Desktop 缺失且手机原图也已删除时，这张照片记为什么、如何提示。
5. **失败重试：** `FAILED` 的照片重试一次。

推算（未实测）：10 万张照片日常跑一次在秒级；MediaStore 重建后全量重算 hash 需要几分钟。

## 循环

```text
触发（新照片 / App 回前台 / 进程启动 / 网络变化回调 / 不可达后 3 次间隔 10 分钟的探测
      / 条件约束任务 / 5h 兜底 / 手动）
→ 在 worker 里检查，不持有 FGS：暂停、后台开关（手动触发除外）、仅 Wi‑Fi、电量、
  今天额度、Desktop 可达、FGS 受阻事实
  任一项不满足 → 登记对应的唤醒，结束
→ 申请 FGS + PARTIAL_WAKE_LOCK（有超时，进度推进时续期）
→ 取件顺序：① 未完成的 order → ② 慢路径标记为补传或重试的 → ③ 快路径的下一张
  每张开始前重新检查上面的条件，并确认 FGS 仍然有效
  hash → 建 order → 传输
  成功 → CONFIRMED（与记账同一次写入）
  单张失败 → 立即重试 1 次，仍失败 → FAILED，继续下一张
  路径失败 → order 保持可续传，退出循环
→ 取不到下一张或条件不满足 → 释放 FGS + wakelock
```

- **FGS 的生命周期 = 循环的生命周期。** 不按单张启停，也不按 App 前后台切换（前台时间不计入 FGS 配额，#411）。
- **传输判定（#410）：** 15 秒没有人来连 → 询问 Desktop 状态，回答 active 就继续等；连接还在、但 3 分钟没有新的文件字节（iroh-blobs `Progress.end_offset` 不前进）→ 主动断开，判为路径失败。
- **传了一半的数据：** iroh-blobs 按块用 bao 边收边验证，续传只补缺失部分。Desktop 把 partial 回收（GC）了就从头再拉，结果依然正确；GC 只影响成本，不影响正确性。

### 失败分三类

| 类别 | 例子 | 处理 |
|---|---|---|
| 路径失败 | Desktop 不可达、握手失败、3 分钟无新字节 | order 保持可续传；退出循环、释放 FGS，登记唤醒；不计入单张失败 |
| 单张失败 | 这一张读不出来、hash 过程出错 | 立即重试 1 次，仍失败记 `FAILED`，循环继续下一张；慢路径再重试一次 |
| 对端失败 | Desktop 明确回报无法接收或保存 | **待定：** #413 未定义处理方式（是否计入单张、是否退出循环、登记什么唤醒） |

## 控制语义

| 状态/动作 | 含义 | 谁可恢复 |
|---|---|---|
| `PAUSED_BY_USER` | 退出循环、释放 FGS，不做任何保活；进程被杀也无妨。任何触发都先检查它，暂停中一律不传 | 仅用户 Continue |
| `WAITING_FOR_CONSTRAINTS` | Wi‑Fi、电量、今天额度或 Desktop 暂不满足：释放 FGS，登记唤醒（网络变化回调 / 不可达后 3 次间隔 10 分钟的探测 / 条件约束任务 / 额度耗尽则等 App 回前台） | 唤醒到来、条件恢复后自动继续 |
| FGS 被拒或超时 | 记下 FGS 受阻事实并退出循环；App 进入前台前不再调用 `startForegroundService`（#414） | App 进入前台 |
| `DISABLED` | 后台开关关闭：自动触发不再启动循环；手动触发不受影响 | 用户重新开启 |
| 取消剩余 N 张 | 把当前还没有结局的 N 张逐张写成 `SKIPPED_BY_USER`（一个事务）；正在传的那张也取消，并通知 Desktop 丢掉已传部分 | 待定：见「取消」 |

## 范围、取消与配对

### 修改范围

改范围当场不做任何处理，下一次查询自然使用新范围。当前这一张（传输中，或暂停时传了一半的）在每次恢复前重新检查：

```text
相册仍在范围内、原文件还在 → 续传
相册已移出范围             → CANCELLED_BY_SCOPE，通知 Desktop 丢掉已传部分
原文件已删                 → SKIPPED_SOURCE_MISSING
```

- 已 `CONFIRMED` 的照片不受改范围影响。
- **待定：** 改范围时正在传的那一张是否当场中断，还是传完再说；「恢复前重检」只覆盖了暂停或中断后恢复的情形。
- **待定：** 新增相册里的历史照片 generation 早于 G，快路径看不到，要等下一次慢路径（App 打开 / 5h 兜底）。改范围时是否立即触发一次慢路径未定。

### 取消

界面上写「取消剩余 N 张」。N 是确认那一刻范围内还没有结局的照片数。

```text
用户确认「取消剩余 N 张」
→ 一个事务内把这 N 张逐张写成 SKIPPED_BY_USER
→ 正在传的那张也取消，通知 Desktop 丢掉已传部分
→ 退出循环，释放 FGS
→ 之后新拍的照片照常进入备份
```

- 慢路径看到 `SKIPPED_BY_USER` 不补传，也不重试；它是用户明确的决定。
- **待定：** `SKIPPED_BY_USER` 的出口——是否保留设置页「已跳过的照片」的恢复入口；恢复时是否把这些 order 翻进补传列表。
- **待定：** 写 N 条 `SKIPPED_BY_USER` 时是否必须当场为每张算 hash（order 以 hash 为身份，N 很大时代价高）。
- **待定：** 取消前是否要求先 Pause。

### 换 Desktop

```text
保留：用户配置与相册选择
清理：partial、运行中传输与旧 Desktop 归属
结果：新 Desktop 从新的备份历史开始
```

**待定：** order 历史按配对归属（`pairingEpoch`）分开的具体方式，以及旧配对的 order 是否保留。

### 迁移

目前没有正式用户，直接清空旧账本。第一次全量慢对账重建 order 表；Desktop 按内容去重，不会重复传输。

