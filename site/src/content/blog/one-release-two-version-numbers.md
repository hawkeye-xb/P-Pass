P-Pass 有两个客户端，macOS 和 Android。自动更新不走应用商店，走我自己维护的更新清单。清单里写着一个版本号，客户端拿自己的号和它比大小，比它小就弹更新提示。

问题是在频繁修构建的那几天冒出来的。有一批改动只碰了安卓，Mac 端的二进制一个字节没变，但按老规矩两端的号一起涨，于是两个平台都弹了一次更新。那几天我一天要发好几个版本，用户就被叫去点好几次。

而这还只是两个端。如果以后加上 iPhone 和 Windows，同一个毛病会放大一倍不止。所以得趁现在把版本这件事想清楚。

P-Pass 是开源项目，很多人直接从 GitHub 下载，所以只能有一个统一的入口。tag 拆成两条线、下载地址也拆成两处，对我来说最省事，Bitwarden 就是这么拆的，`web-v2026.9.1` 和 `desktop-v2026.9.1` 各自存在。可用户不看 tag，只看最新那个 release 里有没有他要的包，一旦拆开就有两个“最新”，他得先判断该去哪一个。只在首页把版本信息聚合一下也不行，那聚合的是展示，入口还是散的。

不同端的更新频率本来就不一样，不能让用户一天被叫去更新好几次。

还有信息对得上这件事。从 GitHub 下载的人，看到的版本信息得和他实际拿到的东西一致。不能让人从 `2026.10.1` 那个 release 里下一个装完显示 0.9.0 的包，还找不到任何解释。

后来要守的东西越来越多，归结起来是两条：用户装上的包，得是我签过名、测过的那一份；他那一端没改，就别去打扰他。版本号只管得了第二条，第一条要靠下载源、验签和流水线门禁一起守。

## 我想先偷个懒

第一反应是给清单加个标记。清单还是共享一条，没变的那一端标一句“本次跳过”。

我去翻了桌面端的更新器，tauri-plugin-updater 2.10.1，源码就在本机的 cargo registry 里躺着。清单结构很直白，版本号只有顶层一个字段，`RemoteRelease.version`；每个平台的条目 `ReleaseManifestPlatform` 里只有 `url` 和 `signature`；判定要不要升级的那一行是 `release.version > self.current_version`。

平台条目里没有写自己版本号的地方，也没有写“这一端本次不更新”的地方。想靠一个标记跳过某端，只能 fork 插件。安卓端的清单是我自己解析的，同样只比一个号。

这条路走不通。要让没变的那一端安静，每一端得有自己的号，客户端只跟自己那端的号比。

## 先去抄作业

Bitwarden 的形态和我这个最像。它的版本号是 `yyyy.mm.r`，官方文档写得很明白，每个月的基础版（`.0`）在客户端和服务端之间共享，之后谁发了 hotfix 谁自己往前走，于是会出现某几端到了 `.1`、`.2`，另几端还停在 `.0` 的情况。

系统层早就这么干了。Ubuntu 24.04、Chrome 130.0.6723.58、安卓的 `versionCode`，都是跟着构建走，不背“这次改了多少”的语义。monorepo 工具也把这两件事当成一等公民，changesets 里一个配置项就能声明一组包是必须一起涨号，还是各涨各的。

两端版本号脱钩也有代价：文档、支持和排障都得写清是哪一端的几号。所以我没走极端，发布这件事本身还是一个共享的批次号，只是每一端交付出去的那个包也有自己的号。

## 定下来的是什么

tag 变成批次号，形如 `2026.10.1`，年月加当月第几版，只往前走不回头，不再等于任何一端的版本号。

每端自己的号写在更新源里，每端一份分端清单，只有这一端真的变了才涨。每个 release 永远两端齐全，没变的那端沿用旧号，包名、包内显示、更新源三处一致。下载入口钉在固定链接上，不指某个具体 release 的资产，因为旧 release 我会清理，那种链接会烂。

别写成 `2026.10.1-2`。在 semver 里 `-2` 是预发布后缀，它比 `2026.10.1` 还小。流水线判断哪个 release 更新时比的就是 tag，这里会直接判错，同一天发第二个批次要写 `.2`。

哪一端该涨号，交给流水线门禁判断。改了 `crates/` 或 `apps/desktop/`，桌面号必须前进；改了 `apps/android/`，安卓号必须前进；只改文档和官网，两端都不该动。它按改动路径判，不看改动的意思，改一句注释也算改了代码。方向偏保守，宁可多发一版，也别漏判。

## 老客户端只认写死在它自己身上的路

真正难的部分是已经装在别人机器上的老客户端。它们的升级路径写在已经安装的那个版本里。桌面端认的是打包时写进配置的清单地址，安卓端先读 R2 上固定路径的那份清单，读不到才回落到 GitHub。

我改清单格式，它们什么都不知道。所以换格式之前必须先发一个两端同号的完整版本，0.9.0，让老客户端先升到它。少了这一步，老客户端要么比不出结果，永远停在旧版收不到更新，要么掉进更难受的循环，新清单的顶层号比自己包里的号大，于是提示更新，装完还是旧号，下次再提示。

## 签名是跟着字节走的

这一条我一开始没想到。清单里的 `signature` 是对着清单指向的那个文件算出来的。我最初把清单里的地址指向 `P-Pass-latest.apk`，看上去很合理，最新的包永远在那儿。可这个名字每版都会被覆盖，下一版一发，老清单里的签名就跟它对不上了，更新直接失败。

后来两种做法都上了：每个版本留一份带版本号、不会被覆盖的副本，老格式的那份清单（老客户端读的那份，内容停在 0.9.0）冻住不再改。

## 发布当晚，安卓端没动静

十月四号晚上发 0.9.0，桌面端升上去了，手机那边一点反应没有。

发布流水线最后一步，是把清单和安装包复制一份到 Cloudflare R2，给国内用户当镜像。这一步挂了，因为它调用仓库里的一个脚本，而那个任务里从来没有 checkout 过仓库，脚本根本不存在。更麻烦的是它挂得很安静：dmg 和 apk 都传完了，清单一个都没镜像出去，页面上看不出任何异常。

为什么到这一版才露头，因为发版事件跑的是 tag 所指那个 commit 的 workflow，而加这一步的改动在更早的 tag 里根本不存在。它加进来之后从没真跑过一次。流水线自己的 bug 也没法靠重跑旧 tag 修，那等于用旧的、有 bug 的流程再跑一次。

救法不用等修复合进主干：在 GitHub Actions 里用修复分支手动触发一次镜像任务，两分钟，R2 上的老格式清单和两份分端清单都对了，手机立刻检查到更新。

## 第一次真发布

第一次真发布是 `v2026.10.1`，桌面端 0.9.1，安卓端 0.9.0。验收挺反直觉，Mac 上检测到 0.9.1 并且升级成功，手机点检查更新显示已是最新。

手机没动静才是对的。这一版安卓的号没变，它不该被打扰。

## 下载源排成一队

官网的下载按钮九月底就换成了 R2 镜像，App 内的更新却还直连 GitHub。十月四号白天我用手机在 5G 下点了一次更新，下载慢得等不下去，国内网络到 GitHub 本来就看运气。

第一反应是让 App 也改走 R2。可只换一个源，等于把单点从 GitHub 挪到了 R2；已经装在别人手机上的老客户端也只认 GitHub 那个地址，丢不掉。

最后客户端拿到的是一个有序列表：先问 R2，再问 GitHub。规则一条条写进了测试。第一个源给出答案，不管是有新版还是已是最新，就停；返回 404 说明镜像还没跟上，接着问下一个；内容读出来解析不了，也接着问；全部问完没人给出答案、中间又有失败，就如实报“检查失败”，不能装成“已是最新”。

R2 后来又多了一条规矩：只放正式版。十月八号回头看十一期间的改动，发现 test 版发布以后，镜像任务会把它当成最新的 release，覆盖 R2 上正式版专用的下载包和清单。test 包用的是同一把签名钥匙，校验能过，正式版用户就会被推一个测试包。这事还没真发生就被翻出来了。现在镜像任务碰到带 `-test.` 的 tag 一律跳过，不管它是怎么触发的；test 通道只从 GitHub 读。

## 两道验签，各误判过一次

自动更新要验两道签名。安卓装包之前，App 用内置的 minisign 公钥验一遍；发布流水线出包时，确认 APK 是用发布 key 签的。两道都出过问题，问题都不在签名本身，在怎么判断验过了。

十月三号第一次在手机上走完整条更新链路，从 0.8.1 升到 0.8.2。检查、弹窗、下载都正常，最后一步报“安装包校验未通过”。点重试，重新下一遍，还是一样。清单里的签名字段装的是整个 `.minisig` 文件的 base64，四行文本；App 却把它当成 74 字节的裸结构来解，长度对不上，直接判失败。每个版本、每次重试都会失败。

单元测试没拦住，因为测试向量是照着实现的写法造的，实现错在哪，测试就跟着错在哪。修的时候把线上 v0.8.2 清单里的签名原文直接写进了测试，另外用 Node 自带的密码学库独立验了一遍，签名和哈希都没问题，错的只是解析。

流水线这边更隐蔽。判断 APK 签没签，看的是 `app-release.apk` 这个文件在不在。没签名、签名方案不满足最低系统版本、用错了 key，这个文件都在。现在改成真跑 `apksigner`：验证必须通过，签名者必须是发布证书，机器上找不到 `apksigner` 也算失败。我拿三个包试过，真发行包通过，没签名的包和用调试 key 重签的包都被拦了下来。

## 流水线的静默跳过

前面那次安卓端没动静，最难受的是页面上一切正常。之后流水线上踩的坑大多是同一种：某一步没跑或者跑错了，后面照样绿。

`v2026.10.1` 发完，Mac 端检查不到更新。macOS 的构建任务被取消了，上传跟着跳过，生成清单那一步看没有 mac 产物，也就跳过了 mac 那份清单。release 页面上什么都不缺，只是 Mac 用户永远收不到这一版。同一次还发现，Windows 版虽然没对外发布，已经在流水线里构建了，它收尾的任务无条件重写了老格式清单，把冻住的那份冲掉了。

第二天发 `v2026.10.2`，安卓的分端清单上传时签名是空的。签名那一步的触发条件还在找一个旧文件名，前一天的改动之后，正式版已经不产出这个文件，整步就被跳过了。

这几处修的方向一样：本该有的东西没有，就让流水线变红。这一版本该有 mac 产物却没有，红；手里有签名密钥、清单签名却是空的，红。另外加了一个运维工作流，拿已发布 tag 现有的产物重算、重签三份清单，不重新构建、不挪 tag，几分钟就能补好一个发坏的版本。

## test 通道走同一条路

test 通道原来是另一套机制。安卓经一个 Cloudflare Worker（跑在 Cloudflare 上的小服务）调 GitHub API 找最新的预发布版本，会被限流，还得配 token；桌面端的 test 版也单独走一段检查逻辑。九月底先把 API 调用拿掉了，改成读一个固定的滚动 release，叫 `test-channel`，每发一个 test 版就把清单覆盖上去。

可两套机制还是两套。test 版测过的流程，不是正式版用户会走的那一条，正式版的坑要等正式发布才露头，上面那几次都是这样。十月十二号把 test 通道改成照着正式版来：同样按端判断要不要构建，同样写分端清单，Mac 的 test 版也用正式版那个插件做应用内更新。

判断要不要构建，基线是 `test-channel` 里这一端清单当前的版本，拿它和这次的 tag 比改动，拿不准就构建。实测发了一个只改安卓的 test 版：流水线判定安卓构建、macOS 跳过，Mac 的 test 清单停在上一版，Mac 没收到提示；三星测试机在应用内升了上去。

## 为什么总在发版后热修

这条链路上的毛病，几乎都要真打一次 tag 才暴露，本地 dry-run 和 PR 上的 CI 都走不到只有 tag 才会走的分支。十月初 `2026.10.1` 和 `2026.10.2` 两版发完，都跟了热修。

test 通道照着正式版来以后，这类坑可以先在 test 版上踩掉。代价是 test 版的流程变长了，按端判断、分端清单、验签，一样不少。

## 现在

十月十二号发的 `2026.10.5` 只修了 Mac 首次启动时的一个问题。Mac 升到 0.9.7，安卓还是 0.9.12，手机上不会出现更新提示。安卓的号从 0.9.0 走到 0.9.12，是因为每合进一个改到安卓的 PR 就涨一次，号在批次之间会跳，用户只在批次发布时收到一次提示。

Windows 版已经在同一条流水线里构建，只是还没对外发布。接进来的时候版本规则没动，多的是一份 `manifest-windows.json` 和判端规则里的一类路径。
