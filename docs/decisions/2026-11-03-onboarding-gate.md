# onboarding 闸门与「连过这台电脑」判据

- 状态：已采纳
- 日期：2026-11-03
- 关联：#1272（配对后直接进照片页）、onboarding 方案（2026-11-03 定案，细节见私仓）

## 结论

1. **进主界面之前必须做过一次「备份哪些照片」的决定**：范围备份，或单张备份，二选一。不允许出现
   「以为在备份、其实什么都没开」。
2. **「连过这台电脑」在决定页做出选择那一刻落盘**，按 daemon node id 记一条只增不减的记录；
   配对成功本身不算。
3. **判据两端一致**：`连过(节点) = 有记录 && 这台电脑的相册范围非空`。范围读不出来按「没连过」
   处理——宁可多问一次，不许把新电脑当旧电脑静默继承。
4. **什么时候走 onboarding**：这台手机第一次用，或连一台从没连过的新电脑。连回以前连过的电脑
   直接回照片页，保留原配置。
5. **决定页只有两个出口**（范围备份 / 单张备份）。照片权限只允许部分或拒绝，落到单张备份，
   不新增第三个出口。范围默认「相机相册 + 从今天起」。
6. **进照片页之后的可选引导**：只有决定页是必经，其余都是可选引导，放在照片页的引导位，同一时间
   最多一张，内容按当前开关现算：没开范围备份 → 引导开启范围备份；范围备份已开、第一张已传成功、
   后台备份未开 → 引导开启后台备份；都开了 → 引导结束。整个可选引导只记一个「onboarding 已走完」
   标记（按手机记，不按电脑）：用户点 × 即记为走完，之后不再出现，断开、换电脑都不重置。
7. **范围里还没有照片是状态提示，不是引导**：在过滤条下方的次要提示位显示一行现状（如「自动备份
   已开启，今天起拍的照片会传到 <电脑名>」），不带按钮，不建议用户改范围；范围里有了第一张照片后
   不再显示；不受 × 影响。
8. **老用户按现状初始化，不写迁移**：升级前已经连过、且这台电脑范围非空的，进照片页时补记。

## 背景

#1272 之后，两端配对成功都直接进照片页；「选范围」只在用户主动打开自动备份时才出现。结果是新用户
扫完码看到的是电脑照片库，手机上一张都没传，而界面上没有任何「还没开始备份」的信号。

两端的「连过」实现也不一致：

- Android：新电脑不落盘，进首页时按「范围非空」补记（`backfillOnboardedOnHome`）。
- iOS：配对成功当场 `finishOnboarding()` 落盘；判据只看记录、不看范围。

另外，「自动备份」规则开关是全局一份（`AutoBackupRulePrefs`）：连新电脑写关，连回老电脑不恢复。
它会不会让「重新连接保持原配置」不成立，单独评估，不在本 ADR 内定。

## 决定

### 记录与判据

- 记录沿用现有 `OnboardedDesktopsStore`（Android `files/onboarded_desktops.json`，iOS 对位存储）：
  一台电脑一条，只增不减；断开、配对失效、换电脑、库升 schema 都不碰它；文件损坏 = 空集合。
- 落盘点从「配对成功」移到「决定页的选择回调」：范围保存成功，或单张备份选完。两端同一时机。
- 判据函数两端同名同义：

  ```
  isKnownDesktop(node) = store.wasOnboarded(node) && scopeNonEmpty(node)
  ```

  `scopeNonEmpty` 惰性求值：标记不在就不去读范围，避免触发 MOB-92 的一次性认领。
- 老用户补记：进照片页时，记录不存在且本机范围非空 → 补记（Android 现有 `backfillOnboardedOnHome`
  同语义，iOS 补一个对位实现）。这就是「读现状初始化」：不迁移数据，只按当前真实状态算初值。

### 状态机

```
配对成功
  ├─ 连过这台电脑 → 照片页（保留配置）
  └─ 首次 / 新电脑 → 决定页
         ├─ 主按钮「选择备份范围」→ 照片权限
         │     ├ 全部允许 → 选范围页（默认相机相册 + 从今天起）→ 开始备份 → 照片页
         │     └ 部分 / 拒绝 → 系统选图 → 照片页（单张备份）
         └─ 次入口「先挑几张试试」→ 系统选图 → 照片页（单张备份）
```

- 决定页是必经步骤，不能跳过；返回/杀进程重来仍回到决定页（记录没落盘）。
- 开启范围备份时两端都进选范围页（Android 现在总是进；iOS 已有范围时直接开始，要改成一致）。
- 后台备份不进必经流程，只在照片页顶部小卡引导；两端动作分别走电池白名单 / 系统设置。

## 理由

- 用户承诺是「手机照片自动备份到这台电脑」。没有范围就没有可备份的内容，先做决定再给主界面，是
  同类产品（iCloud 照片、Google 照片、Synology Photos）的常规做法。
- 「连过」必须由**用户行为**（做了决定）定义，而不是由**网络事件**（配对成功）定义：配对成功但没选
  范围，用户并没有表达备份意图。把配对当连过，正是这次「扫完码直接进照片页」的根因。
- 按电脑记记录、按电脑读范围，才能让 macOS → Windows → macOS 不把 Windows 的范围当成 macOS 的。
- 只增不减 + 读现状初始化，符合「尊重用户已有的选择、不写迁移」的产品硬规矩。
- 蒙层式引导打断性强、多数会被跳过，所以必经的只有决定页；其余按当前状态就地提示，点 × 尊重
  用户不想继续。用户选了「从今天起」就是做了决定，空状态只说现状，不劝用户改范围。

## 后果

- iOS 现在「配对即落盘」的行为要改；已经落盘的老用户记录仍在，不受影响。
- 新电脑第一次会多一屏（决定页）；连回老电脑不增加步骤。
- 需要新增决定页（两端）、照片页引导位（开启范围备份 / 开启后台备份）与范围内无照片的次要提示，
  文案改动按产品流程过。现有零散引导（如「还没有选择相册」）并入引导位的第一步。
- 判据从「配对成功」改为「做了决定」，`finishOnboarding()` 这类入口要一起收口；测试要钉「配对成功
  不落盘、决定后落盘」。
- 全局 `AutoBackupRulePrefs` 与「连回老电脑恢复原配置」的冲突另开评估卡，不在本 ADR 内。

## 备选（未采纳）

- **以「配对成功」为连过**（现状 iOS）：扫完码就被当成连过，决定页永远不出现，这次要解决的问题
  原样保留。
- **全局 onboarding（一台手机只问一次）**：连新电脑会静默沿用旧范围或被写关备份，违背「按电脑算
  范围」，也让「连新电脑」这条产品规则落不了地。
- **以「范围非空」为唯一判据**：一台从没连过的新电脑可能因为 MOB-92 的一次性认领继承老的全局范围，
  被误判成连过——这就是现在 Android 补记逻辑的已知风险。
- **另起一套 onboarding 记录文件**：与 `OnboardedDesktopsStore` 重复，两处判据必然漂移。
