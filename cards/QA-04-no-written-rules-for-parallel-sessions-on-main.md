## 挂号段

- **现象**：`AGENTS.md` 里与"多会话同时在 main 上干活"相关的只有三句半——
  红线 5「红测不进 main → 推 `wip/<卡号>`」、「换卡必换会话」、「卡间关系只以

  怎么先看一眼别人正在做什么。
- **发现场景**：2026-09-17 验收人问「现在很多人在做项目，过程中怎么做？
  这里有指引吗？」。查完确认没有。而当天 main 上已有 **24 个提交、至少 3 条
  并行工作流**（我这边 IDX-01/NET-25/QA-03/BUILD-05，另一边
  NET-15/NET-16/TEL-05/TEL-03），15:06–15:27 的 21 分钟里两个会话交替推了 6 次。
- **严重度猜测**：中高。今天没出事，但**全部依赖临场判断**：我遇到的五种情况
  （见下）每一种都可以做成另一种更糟的样子，而规范不会拦住。

## 备注（挂号时已核实，供接卡人省一次考古）

**今天实际遇到的五种情况 + 我当时怎么处理的**（这就是草案的素材，全部有据）

| # | 情况 | 我的处理 | 如果换个做法会怎样 |
|---|---|---|---|
| 1 | push 被拒（远端已前进） | `git fetch` 看清对方改了什么，再 `git rebase`，历史保持线性 | `git pull` 默认 merge → main 长出交叉历史，二分变难 |
| 2 | 账本冲突（PROGRESS/QUEUE） | 手工留两边；**保留对方的排布不动**，只插自己那行 | 只留自己那边 → 静默吞掉别人的交付记录 |
| 3 | 撞到别人的红测 | 二分定位（只把那一个文件退回父提交）→ **测完原样还原** → 挂号 + 当场汇报，不改对方代码 | 顺手"修"别人的卡 → 两个会话同时改同一处；或装没看见 → 红留在 main |
| 4 | 要动共享文件 `tools/` | 先 `git log origin/main -5 -- tools/` 看对方在不在动同一批文件，选了不重叠的那个 | 直接改 → 真代码冲突，不是一行账本 |
| 5 | 自己的门禁会让 main 变红 | 断言与那 8 处修复**同一个提交**落地 | 分两次 → 中间那一刻 main 红，连带把别人的 ci-docs 搞红 |

**建议写进 `AGENTS.md` 的草案**（措辞待验收人定；本卡**不擅自改 AGENTS.md**）

1. **同步一律 `git fetch` + `git rebase`，不用 `git pull`。** 理由：main 要保持
   线性，二分才有用——今天 NET-26 就是靠单文件二分定位的。
2. **push 被拒不是错误，是常态。** 先 `git log main..origin/main` 看清对方改了
   什么再 rebase；对方动过的文件与自己重叠时，读一遍 diff 再继续。
3. **账本冲突手工解，两边都留，不动对方的排布。** `docs/PROGRESS.md` /
   `docs/QUEUE.md` 是每张卡必经之地，冲突是结构性的、不是谁的错。
   ⚠️ 不要给它们配自动合并（QA-03 已证伪：`merge=union` 的残留与正常历史
   不可区分）。
4. **撞到不是自己造成的红测**：二分定位 → 原样还原 → 挂号 + 当场汇报，
   **不改对方代码、不顺手"帮修"**。红线 5 的「红测不进 main」约束的是自己引入
   的红；别人已经在 main 上的红，处理方式是挂号和汇报。
5. **动共享文件（`tools/`、`justfile`、`.github/`、`AGENTS.md`）之前**，先看
   `git log origin/main -5 -- <路径>`。撞上了就换个时机或换个文件，别硬上。
6. **会让门禁变红的改动，必须与让它变绿的修复同一个提交。**
7. **开工前先看一眼别人在做什么**：`git log origin/main -10 --oneline` +
   `docs/QUEUE.md` 的状态列。这一条其实已经隐含在「开工按 session 类型分流」里，
   但没写明并行场景。

**接卡人注意**：以上第 3、6 两条与现有红线 5 有交集，措辞要一起看，别写成两套
口径。另外 `AGENTS.md` 开头就写着「一页化」，加这一节要控制篇幅——建议压成
一个小节 5–7 行，细则放本卡。
