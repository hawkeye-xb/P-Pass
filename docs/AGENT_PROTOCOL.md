# AGENT_PROTOCOL — 铁律与门禁

> 本文档为实施计划 §B 的原文落库。工程门禁由 `tools/arch-check.sh` 和 `.github/workflows/pr.yml` 强制执行。

## §B.1 iroh 隔离规则

**规则：** `iroh` 只允许出现在 `crates/transport/` 中。

**覆盖范围：**
- `.rs` 文件中的 `use iroh...`、`iroh::...`、`extern crate iroh`
- `Cargo.toml` 中的 `iroh = ...` 依赖声明

**执法：** `tools/arch-check.sh` B.1 段以 grep 扫描 `crates/` 目录（排除 `crates/transport/`）。CI 中 `just arch-check` 失败即阻断合并。

## §B.2 平台 cfg 隔离规则

**规则：** 包含 `cfg` 且同行出现 `windows` 或 `target_os` 的代码只允许出现在 `crates/platform/` 中。

**覆盖范围（三种写法，宁误报不漏报）：**
- `#[cfg(windows)]`、`#[cfg(target_os = "...")]`
- `#[cfg_attr(any(...), cfg(windows))]` 等属性宏形式
- `cfg!(windows)`、`cfg!(target_os = "...")` 等编译时宏形式

**执法：** `tools/arch-check.sh` B.2 段以正则 `\bcfg\b.*\b(windows|target_os)\b` 全量扫描
`crates/` 目录（排除 `crates/platform/`）。platform crate 内豁免。

## 铁律摘要

| # | 铁律 | 执法方式 |
|---|------|---------|
| 1 | 只做当前卡 | 人工抽查 diff 范围 |
| 2 | 不准为绿而改旧测试；架构已取代其契约时，先冻结旧卡/测试、按新 case 重写 | 人工抽查 + 架构卡 case matrix |
| 3 | 禁止捏造命令输出 | 卡片验收要求贴真实输出 |
| 4 | 凭据不进代码 | `.example` + env 约定 |
| 5 | iroh 只许在 transport | `just arch-check` → B.1 |
| 6 | 平台 cfg 只许在 platform | `just arch-check` → B.2 |
| 7 | 每卡收尾 just 全绿 + PROGRESS.md | CI + 人工抽查 |

# §C 任务分级与可验证验收

> 由来（2026-08-03）：一批外派卡出现系统性的"声称的绿 ≠ 真的绿"——
> 恒真判据（`-match "缺 0\|0 个"` 必命中"50 **0 个**"）、soft-fail 仍报
> ALL GREEN、"CI 绿"当验收、把未合并兄弟卡的修复写成"已落地"。§C 的
> 目的就一个：**让"绿"不可造假**。派卡人按 §C.1 定级、按 §C.2 填模板；
> 实施 agent 按模板交付；验收人按 §C.3 抽检。

## §C.1 任务分级（决定派给谁 + 验收档位）

| 级别 | 任务类型 | 派给 | 验收档位 |
|---|---|---|---|
| **L0** 机械 | 改文案 / 删重复 import / 同步文件 / 重命名 | 最低成本 agent | CI 绿即可 |
| **L1** 局部 | 单文件 bug / 判据加固 / 配置修正 | 中等 agent | 相关测试红→绿 + **反证**（见 §C.2）|
| **L2** 跨模块 | 新协议 / 校验机制 / 架构改动 | 强 agent | 对抗性 review + 真机/真数据 |
| **L3** 真环境 | VPS / 真机 / 构建发布 | 运维 agent / 平台 agent / 人 | **实证输出**（日志 / 截图 / 健康检查）|

定级看的是"错了谁能发现"：L0 编译器/CI 能兜；L1 要测试证明；L2 要独立视角对抗；
L3 只有真实环境能证伪。**定不准就往高一级放**。

## §C.2 任务卡模板（外派卡必须填满，缺字段=不受理）

**模板文件：`cards/TEMPLATE.md`**——复制开卡。必备头部五段：

```
## 卡号 标题（状态横幅：✅归档 / 🟡待真机验收 / ⬜未开工）
## 问题      —— 现象 + 复现步骤，不假设读者看过别的卡
## 期望行为  —— 修好后应该什么样
## 验收标准  —— 可逐条打勾的判据（不接受"应该 work"）：
  - 跑 `<命令>` → 期望 `<可复现的具体输出>`
  - （L1+ 故障/安全类必带反证）跑 `<把故障条件去掉的变体>` → 必须变红，
    证明判据不是恒真式 / 不是 soft-fail
## 范围      —— 只准动这些文件/目录 + 明确"不准动"的相邻物（越界即违反铁律 1）
## 阻塞与依赖 —— 等拍板的决定 / 前置卡 / 需要的环境

**目标**：一句话说清"做完什么算完成"。
**证据要求**：报绿必须附命令 + 输出摘要。**CI 绿不是唯一证据**——
  声称"X 测试绿"就要贴 X 的真实输出，只跑了一半不算。
**跨卡声明禁令**：不许写"兄弟卡 Y 已修复/已落地"。Y 未合并进 main 时
只能写"待 Y 合并后成真"，或把该依赖项显式列为本卡的前置。
**架构换代时的旧测试**：旧测试保护的是旧实现细节，而已确认的架构卡重定义
了该流程时，旧测试不许继续作为新实现的门禁，更不许让 agent 为它保留旧机制。
先在旧卡写明 frozen/superseded 及对应的新架构卡；保留下来的产品不变量从新
case matrix 重新写成失败用例，再开始生产实现。
**本机状态禁令**：本机路径、设备序列号、开发机用户名不进卡，
这类信息只属于 `local-state.md`（不进 git）。
**收尾**：just 全绿 + 更新 ROADMAP 对应行 + PROGRESS.md 一行。
```

## §C.3 验收人抽检法（低成本高杠杆，不重跑不重实现）

验收不是把 agent 的活重做一遍，而是**对抗性抽检**——只读 diff，专挑造假高发点：

1. **恒真式判据**：`grep`/`match` 的模式串会不会必然命中？（子串陷阱、
   `-z`/空集恒真、`|| true` 吞错）
2. **soft-fail**：失败路径是不是只打印警告却仍走到 ALL GREEN？尤其安全语义
   （吊销、鉴权）必须 hard-fail。
3. **"绿"的覆盖面**：声称的"全绿"实际跑了哪些？有没有只跑一半就报全绿？
4. **跨卡声明**：文档/ROADMAP 里"已修复"的东西，在 main 上真的存在吗？
   （`git grep` 一句话验证）
5. **反证是否成立**：故障类卡，把故障条件去掉后判据会不会变红？不会=判据假。

抽检发现任一条→打回返工，不合并。逐条核实量大时并行 review agent 承担，
验收人只读结论做裁决。**验收人不做构建/打 tag/盯 CI/真机跑**——那是 L3，外派。

# §D 推送纪律（2026-08-10 用户特批：速度优先阶段）

单人冲 MVP 阶段，**允许直推 main / 自 merge，不用等 review**——PR 等待
成本高于漏审成本，这是用户的显式裁决（覆盖 §C.2 模板里的「走 PR 等
review」收尾行）。代价是三条底线，破一条按事故处理：

1. **CI 绿不过夜**：push 后盯 main 的 Checks 到结论，红了立刻修或 revert。
2. **每批交付必更文档**：PROGRESS 每卡一行 + NEXT 队列 + ROADMAP 状态行。
3. **验收人事后抽检有 revert 权**（§C.3 照常适用，只是从事前挪到事后）。

tag 只打给准备真发的版本；调管线用 workflow_dispatch。速度优先阶段到
有外部用户/第二个贡献者为止，届时本节作废、恢复 §C.2 原文。
