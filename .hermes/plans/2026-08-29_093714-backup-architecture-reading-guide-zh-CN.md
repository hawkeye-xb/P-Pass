# P-Pass 备份架构：中文阅读版（仅设计，未实施）

> **状态：历史阅读稿。** 当前规范请使用 `2026-08-29_114911-backup-core-flow-decision-record-zh-CN.md`；其中已固定 500 项发现窗口、Pause 仅暂停消费者及外部删除默认待决策等后续结论。

> 这份是手机阅读用的中文总稿。它只解释已经讨论出的架构方向、已经确认的产品语义，以及还必须拍板的核心问题；不代表任何代码已经改完。

## 一句话目标

备份不是“某个后台任务跑完了”。

> 一张被发现、且在用户备份范围内的照片，要么已得到电脑端的可靠确认，要么仍明确记录为待传、等待、重试、用户取消或永久失败；绝不能因为 App 被杀、网络变化、暂停或系统取消而悄悄消失。

## 已经确认的产品语义

### 1. 自动备份

```text
自动备份 = 系统自行决定何时备份

后台自动开启：App 在后台时也可自动发现、自动传输
后台自动关闭：App 在后台时不发现、不传输
前台打开 App：无论后台自动是否关闭，默认都可以自动备份
```

关闭后台自动备份不是删除待传照片，也不是用户暂停。

### 2. Pause、Continue、Cancel

```text
Pause
  用户要求当前备份管线不要自动继续

Continue
  恢复原来的未完成队列；不是重新全量扫描

Cancel
  用户明确放弃“本次传输”里尚未确认的内容；
  手机与电脑两侧都要清理活跃传输/staging 记录
```

### 3. 单文件永久异常

```text
文件不可读 / 被删除 / 协议明确拒绝 / 重试预算耗尽
  → 留下错误原因
  → 标为永久失败
  → 清理两侧活跃传输记录
  → 继续后面的正常文件
```

坏文件不能阻塞整批，也不能假装已经备份成功。

## 架构的核心分层

```text
界面层
  只显示状态、发送用户命令
      ↓
应用层
  统一的备份控制器：发现、传输、暂停、继续、取消、对账
      ↓
领域层
  纯业务规则：什么能传、哪个文件可重试、什么叫成功/取消/失败
      ↓
接口层
  业务需要的能力：状态库、媒体扫描、远端传输、调度、运行条件
      ↓
适配层
  Android MediaStore、Room/SQLite、WorkManager、JobScheduler、daemon 协议
```

### 这几件事必须彻底解耦

```text
MediaStore
  只回答：手机有什么本地媒体变化？

WorkManager / JobScheduler
  只回答：现在能不能/什么时候叫醒执行器？

远端 daemon / staging
  只回答：如何协商、传输、清理临时文件？

本地 BackupState 数据库
  唯一回答：哪些项已发现、待传、已确认、已取消、失败、待清理？
```

因此，不能再用 Work 名称、Work 状态、某个偏好布尔值或远端 staging 是否存在，来猜“用户是不是暂停了”或“文件是不是已完成”。

## 核心持久数据

```text
备份策略
  用户选了哪些相册、后台自动是否开启、自动备份条件、下次对账时间

发现游标
  本地相册变化已经可靠写入待传账本的位置
  不是“已经上传完成的位置”

传输意图
  一次可被 Pause / Continue / Cancel 控制的传输范围

传输项
  一个具体媒体版本：待传、占用中、等待重试、已确认、永久失败、用户取消

远端确认账
  远端何时确认拥有过哪个内容版本

清理待办
  用户取消或永久失败后，电脑端 staging 仍需清理时留下的可靠 outbox
```

最关键的事务：

```text
扫描到新照片
  → 同一数据库事务写入“待传项” + 推进“发现游标”

事务成功前崩溃：下次重扫，最多重复发现
事务成功后崩溃：待传项仍在，绝不丢照片
```

## 传输主线

```text
触发（Watch / 前台 / 周期 / 手动 / 对账）
        ↓
统一备份控制器
        ↓
检查：前后台、自动开关、范围、Wi‑Fi/电量、暂停状态
        ↓
扫描本地变化，原子写入待传项 + 游标
        ↓
从“最早可传”的待传项中取一个
        ↓
哈希、去重、传输、远端确认
        ├─ 成功：写已确认
        ├─ 暂时失败：只延后这一项，继续后项
        ├─ 永久失败：记录原因、清理 staging、继续后项
        └─ 系统停止：释放占用，回到待传；不等于暂停/失败
```

## 当前 main 实现到底有什么

当前不是没有能力；它已经具备不少正确的局部能力：

```text
- MediaStore 增量扫描：按水位发现本地变化
- 相册范围闸门：未选范围 / 空范围不传
- 哈希缓存与远端 manifest 去重
- 已确认内容缓存：用于进度和低频远端对账
- 定向补传：远端缺失的旧照片不必全量重扫
- 坏媒体记录隔离：一条打不开的本地记录尽量不炸整批
- 多个触发来源：监听、前台、冷启动、周期、手动
```

但这些能力目前组合成的是：

```text
五个触发入口
  → 多个 WorkManager name
  → 一个很大的 BackupWorker
       校准 + 范围 + 扫描 + 补传 + 哈希 + 传输 + commit + 水位 + 通知
  → 多个分散 JSON 状态文件
```

当前 Worker 的批次形状是：

```text
扫描候选
  → 哈希全部候选
  → begin
  → manifest
  → 上传本批缺失文件
  → commit 整批
  → 保存新水位
```

也就是说，当前“确认”与“推进水位”的主要边界仍是整批 commit。

## 当前存在的结构性问题

### 1. 发现、待传、已确认三件事没有独立账本

当前水位要等整批成功后才推进；这是为了防止“先推进水位、随后崩溃导致候选永久丢失”。它是安全的补救，但代价是：

```text
中断 / 重启
  → 从旧水位重扫
  → 依赖远端去重收敛
```

系统没有持久的“这些项已经发现、但还未确认”的统一队列，因此不能真正从某个未完成项精确继续。

### 2. 状态被拆散，无法做原子一致的业务转换

当前至少分散在水位、确认账、补传队列、暂停时刻、自动开关、失败次数等状态文件里。它们各自崩溃安全，但彼此不是一个事务。

所以很难可靠表达：

```text
发现项 + 推进游标
暂停意图 + 停止执行器
取消项 + 两侧清理待办
确认项 + 更新确认账
```

### 3. Pause 是“UI 标记 + 取消当前 Work”的组合，不是完整控制状态

当前 UI 运行中点击会记录暂停时刻后 `cancelWorkById`；而不在运行中再次点击会进入手动全量触发。这会把 Continue / Retry 的业务语义偷换成：

```text
零约束 + 全量扫描的 Manual
```

另外自动开关当前在 Worker 入口作为全局闸门，和“关闭后台自动、但前台打开 App 仍默认自动备份”的新产品语义不一致。

### 4. 当前协议的可靠确认是批次级，而产品需要项级

远端协议目前是 `begin → manifest → 上传 → commit`。一项永久异常后要“清理它、继续其他项、每项独立确认”，需要把 transport session 与业务队列解耦；仅在现有批次 Worker 里追加分支解决不了。

### 5. 取消两侧暂存还没有可靠的业务契约

当前远端有 session/staging 与超时回收，但没有以“用户取消某个传输意图”为中心的显式清理协议与本地 cleanup outbox。

如果只在 UI 点击时发一次取消请求：

```text
本地已取消，但电脑离线 / App 崩溃
  → 远端暂存可能残留
```

这正是为什么需要 `cleanup=Pending` 与独立清理重试，而不是把取消等同于结束。

### 6. 特殊补偿路径在增长

定向补传、范围补齐、校准、前台补捞、监听重挂都各自解决了真实问题；但它们目前是围绕主批次流程增加的特殊入口。继续沿这条路径扩展，新的触发或设置变化仍容易漏接某一个分支。

## 我的建议

### 不建议

```text
- 不要现在直接改名五个 WorkManager 任务
- 不要再给 Pause / Retry / 自动开关多加几个 if
- 不要先做 UI
- 不要让 WorkInfo、unique name 或 JSON 偏好文件继续充当业务真相
```

### 建议的路线

```text
第一步：先定 P0 语义
  交付确认、Cancel 边界、Pause 发现策略、媒体版本身份

第二步：先做纯业务状态机与 case 测试
  不碰 Android、不碰网络，先证明状态转换是对的

第三步：引入一个统一状态库
  原子保存“发现项 + 游标”，并保存 queue / control / evidence / cleanup outbox

第四步：把现有扫描和传输包成 adapter
  MediaStore 只负责找媒体；现有 daemon 协议只负责传输

第五步：最后才收拢 WorkManager、监听、前台与 UI
  它们都只发 wake 或 command，不再各自决定业务策略
```

这是**渐进替换**，不是推倒重写：现有扫描、哈希、去重、远端传输、范围补齐能力都可以保留为 adapter；替换的是“谁拥有业务状态、谁决定下一步”。

## 目前最需要先聊透的 P0 问题

### P0-1：什么时刻才叫“这张照片已经交付”？

当前协议是：

```text
开始批次 → 提交整批清单 → 上传缺失文件 → 整批提交
```

也就是说，当前确认边界是“整批提交”，不是“单文件确认”。

但我们想要的行为是：一张坏文件失败后，后面的继续传；每张成功的文件立刻可靠确认。

必须定：

```text
A. 第一版：每项单独走一次现有传输会话，先换正确性
B. 改协议：一个会话内支持逐项确认、逐项 abort，性能更好但工作更大
```

建议：领域模型按“每项确认”设计；第一版可先用 A，协议优化独立做，不让性能优化反过来污染业务语义。

### P0-2：Cancel 的“本次传输”到底是哪一组项？

连续队列天然没有“这一轮”的边界。必须选一种：

```text
A. 取消暂停时刻所属的一次传输快照      ← 推荐
B. 取消当前队列里所有未确认项
C. 以后由用户在 UI 中选具体项
```

没有这个答案，就不能定义 Cancel 的范围，也不能保证两侧 staging 清理正确。

### P0-3：Pause 时还要不要继续“发现”新照片？

```text
严格暂停（当前暂定）
  不扫描、不入队、不传输；Continue 后再扫描

仅暂停传输
  仍扫描并写入本地队列，但绝不联网传输
```

前者最符合“暂停备份就是停”；后者恢复更快、待传数更准确，但 Cancel 范围和用户预期更复杂。这个需要明确。

### P0-4：一个“媒体版本”怎样定义身份？

需要区分：

```text
同一张照片移动相册 / 改名       → 不应重复上传
同一条 MediaStore 记录内容被修改 → 应当成为新的待确认版本
不同文件内容 hash 相同          → 可远端去重，但文件级确认仍要准确
```

建议的候选身份：

```text
远端身份 + MediaStore 稳定引用 + 本地版本信息
（generation / 修改时间 / 大小）
```

哈希在真正读取后补上，用于远端去重和确认。

### P0-5：范围缩小、扩大、移动相册时怎么办？

必须写死：

```text
缩小范围：已入队但新范围外的项是否立刻取消并清理 staging？
扩大范围：水位以前的旧照片怎样被发现？
相册之间移动：是否根据当前范围重新裁决？
```

当前推荐：缩小范围立即终止范围外待传项；扩大或移动进范围时走“范围补发现”，不把全局发现游标倒退。

### P0-6：暂时失败与永久失败怎样裁决？

需要统一分类表，而不是每个 catch 自己猜：

```text
暂时：断网、超时、远端暂不可达、系统停止
永久：本地文件不存在/不可读、权限永久失效、协议明确拒绝
待定：磁盘满、配对失效、远端空间不足、hash 不一致
```

待定类必须决定：重试多久、何时需要用户处理、是否阻塞后项（默认不阻塞）。

## 讨论顺序建议

```text
先谈：P0-1 交付确认 + P0-2 Cancel 范围
再谈：P0-3 Pause 发现策略 + P0-4 媒体版本身份
然后：P0-5 范围变化 + P0-6 失败分类
最后：后台切换细节、对账周期、UI 文案与视觉表现
```

这些 P0 定下来以后，状态机、数据库 schema、传输协议和测试 case 才能一次成型；否则现在开始写代码，必然又会回到补丁式讨论。
