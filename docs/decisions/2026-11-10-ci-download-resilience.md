# CI 与发布链外部下载的韧性与缓存

- 状态：已采纳
- 日期：2026-11-10
- 采纳：产品负责人 2026-11-10 在 #1595 拍板「方案 A：与 #1589 同模式补上」
- 关联：#1589（PR 链的重试与缓存）、#1594（实现）、#1595（本方案覆盖的剩余路径）、#1619

## 背景

CI 与发布链直接依赖多个外部下载：GitHub Releases（gitleaks、actionlint、osv-scanner、XcodeGen）、services.gradle.org（Gradle 发行版）、vcpkg 引导、codec 源码、ffmpeg。2026-11-09 GitHub 出口抖动，多处下载 504/超时，把 PR 的必需检查判红、把发版卡住。

#1589 已在 PR 链上落地「重试 + 缓存」（PR #1594 已合入），实测有效：Gradle 发行版缓存命中后整条 job 0 次下载。剩下 release.yml、e2e.yml 的 Gradle 与 `tools/fetch-ffmpeg.sh` 还没有覆盖。

## 决定

采用方案 A，与 #1589 完全同模式：

1. `release.yml`、`e2e.yml` 里的 Gradle 步骤接与 `ci-android` 相同的发行版缓存（按 `distributionUrl` 做 key，只在成功时保存）。
2. `tools/fetch-ffmpeg.sh` 的 curl 加 `--retry 5 --retry-delay 2 --retry-all-errors -fL`，sha256 校验不变。
3. 不引入镜像站；不改变任何下载内容与校验逻辑。

## 理由

**本质要保证什么**：CI 和发版链的成功率不应由第三方出口的瞬时故障决定。重试吸收瞬时抖动、缓存消除重复下载，是两层标准做法。

**标准做法**：下载加指数退避重试；不变产物做内容寻址缓存。#1589 已在本仓实证，直接沿用同一模式，不发明新机制。

**为什么不做镜像（方案 B）**：镜像要多维护一份二进制与更新流程，且引入「镜像与上游不一致」的新风险；当前重试 + 缓存已能覆盖大部分抖动，先不增加维护面。

## 后果

- `release.yml` 属更新链核心，本 ADR 合入 main 后，#1595 的实现 PR 正文引用它，acceptance gate 才放行。
- 下载失败时的表现不变：重试耗尽后如实失败，不会被静默吞掉。

## 备选

- **方案 B：镜像到 p-pass-dl**：更彻底，但多一份镜像维护与更新流程；留作后续可选，不在本次范围。
