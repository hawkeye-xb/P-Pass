三星真机的系统日志里，某天出现了这两行：

```
14:35:50  ActivityManager: Killing ...com.hawkeyexb.ppass (adj 915): one-time permission revoked
15:51:35  ActivityManager: Killing ...com.hawkeyexb.ppass (adj 900): one-time permission revoked
```

系统在传输过程中，把 App 杀了。两次。

`adj`（oom_score_adj）是 Android 给进程打的"死活优先级"分数。数字越大越容易被系统回收，900-915 这个区间是"缓存进程"档——系统认为你已经不在做什么要紧事，随时可以为了腾内存把你干掉。而一个正在给用户传照片的进程，理应处在前台服务那个受保护的档位（通常是两位数以内）。

## 复现：切到后台那一刻，保护就没了

用干净的测试相册，推 35 张 6MB 的图触发一次真实传输，传输进行中按 Home 键切后台，每隔几秒采样一次 `/proc/<pid>/oom_score_adj`：

```
t=0s    （刚切后台）        adj=700
t=+60s  （传输仍在进行）    adj=700   ← 不变，从头到尾没被提升过
传输完成后                  adj=900
```

`dumpsys notification` 确认通知栏**从头到尾没有任何前台服务通知**。系统日志里有一行更直接：`pkgName: com.hawkeyexb.ppass is not in foreground`——系统压根不知道这个进程正在干一件不该被打断的事。

## 根因：一次"减负"重构，把保护也一起减掉了

往回查提交历史，找到了源头。几周前有一次重构，把负责传输的 Worker 从 1147 行削减到 125 行，改造成一个纯粹的"唤醒适配器"——它不再自己跑传输逻辑，只负责把系统的唤醒信号转交给新的传输引擎。这次削减是对的方向，旧代码确实臃肿。

但旧代码里有一段容易被忽略、却承担着关键职责的代码：

```kotlin
// 被删掉的旧代码（示意）
override suspend fun doWork(): Result {
    setForeground(foregroundInfo())   // ← 这一行
    // ... 传输逻辑
}
```

`setForeground()` 是 Android 里"告诉系统：我正在做用户能感知到的事，请给我前台服务级别的保护，别把我当缓存进程杀掉"的那一句话。旧 Worker 里这句话紧贴着传输逻辑本身，重构时传输逻辑被整段搬到了新的引擎里，这一句保护性的调用没有跟着搬——它既不属于"业务逻辑"也不属于"唤醒逻辑"，两边都觉得这不是自己的事，于是谁都没接。

新的传输引擎完全跑在一个独立的协程作用域里，从未挂靠任何 Android 系统组件的生命周期。没有 Service，没有 Worker 的 `doWork()`，也就没有任何地方能调用 `setForeground`。

Manifest 里保护相关的权限声明和服务类型都还在——`FOREGROUND_SERVICE_DATA_SYNC`、`dataSync` 类型的 Service 声明，一行没删。但这是一个空壳：声明本身不会自动生效，它只是告诉系统"如果我调用前台服务 API，我有权限"，从没有代码真的去调用它。**权限声明齐全，不等于保护真的存在**——这句话读起来像常识，但恰恰是这次事故最直接的教训：审查一次删减，光看"删掉的代码是不是没用了"不够，还要问"这段代码除了看得到的职责，有没有承担一个别处都看不出来的隐藏职责"。

## 修复：把保护挂在一个不会被漏掉的收尾点上

修复没有把保护逻辑塞回某个具体的调用点——那样太容易在下一次重构时又被漏掉。而是找到了新架构里唯一一个"每次传输动作最终必然会经过"的收尾函数，把保护挂在那里：

```kotlin
// AndroidFlowRuntime.flushAuditOutbox 是每个 Flow 触发动作
// 最终都会走到的收尾点——不依赖任何调用方"记得"单独调用
FlowTransferForeground.sync()
```

这个前台服务本身很朴素：有传输在跑，就 `startForeground`；没有，就降级。决定要不要提升保护级别的逻辑被写成了一个独立、可单测的纯函数，输入是"这一轮传输是否活跃"这个既有的账本事实，输出是"该不该保持前台"。

## 验证：不只是"改完看起来对了"

先写了一个反证：临时把新加的那一行调用注释掉，对应的测试立刻失败——测试断言"每个传输触发出口最终都必须调用一次前台服务同步"，删掉调用点后这句断言不成立，恢复后重新通过。这证明测试锁住的是真实的调用关系，不是摆设。

真机复测：同样的 35 张图、同样切后台、同样每隔几秒采样：

```
全程 adj 锁定在 200（前台服务保护档位）
不再是修复前的 700-900（可回收的后台缓存档）
```

`dumpsys activity services` 确认服务确实处于 `isForeground=true`。35 张全部传输确认成功，全程没有再出现进程被杀的记录。

## 这里的教训

重构"减负"的时候，最容易被漏掉的不是那些一眼能看出用途的代码，而是那种**贴着别的逻辑、看起来像是那段逻辑的一部分、实际上承担着完全独立的系统职责**的代码。`setForeground()` 长得像是传输逻辑的一部分，实际上它跟"传输逻辑本身该怎么写"毫无关系，它回答的是另一个问题——"系统该不该保护我"。这两个问题被写在同一个函数里，删代码的时候很自然地被当成一个整体处理掉了。

这次修复之后留的一条防御，不是"以后重构小心点"，而是把这类保护性调用挂在一个**结构上不可能被漏掉**的收尾点，而不是指望每个未来的调用方都记得手动加一句。人会忘，收尾点不会。
