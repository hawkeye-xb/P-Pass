# 升 sqlx 0.9 修复 bundled SQLite 的 CVE

- 状态：已采纳
- 日期：2026-11-12
- 采纳：产品负责人 2026-11-12 把 #1629 放进 milestone 0.12.x（要做）
- 关联：#1629、#1628、#1595

## 背景

2026-10-30 的安全公告 RUSTSEC-2026-0459（CVE-2026-119375）判定 `libsqlite3-sys < 0.39.0` 有漏洞：SQLite 3.54.0 之前，当一个数据库文件旁边有页大小不同的 `-wal` 兄弟文件时，普通查询可能返回进程内存里的残留字节。CVSS 4.0 `AV:L/AC:L/PR:N/UI:P/VC:H`（本地、需受害者打开文件、机密性高）。

我们是 bundled SQLite：`sqlx 0.8.6` → `sqlx-sqlite 0.8.6` → `libsqlite3-sys 0.30.1`（bundled SQLite < 3.54），命中。

修复只在 `libsqlite3-sys >= 0.39.0`，而 `sqlx 0.8.x` 固定 `libsqlite3-sys = "0.30"`、没有补丁版本——只能升 sqlx 0.9。

## 决定

把 sqlx 升到 0.9 的最新补丁版，同步适配 `crates/storage`、`crates/core-index`、`crates/daemon` 三处的 sqlx 用法；从 `deny.toml` 移除 RUSTSEC-2026-0459 的忽略项。

## 理由

**本质要保证什么**：用户存在电脑上的照片库索引，不该因为一个已知的 SQLite 缺陷泄露别的进程内存。这是「不可挽回·安全」类问题，即便实际利用门槛高（需要本地写权限 + 用户交互打开文件）。

**标准做法**：上游已给出修复（`libsqlite3-sys >= 0.39.0`），标准解就是升到带修复的依赖版本并删掉 CVE 忽略项，而不是继续压住告警。不造轮子、不自己打补丁。

**偏离说明**：无。升 sqlx 0.9 是上游给出的唯一修复路径。破坏面已知且范围明确——sqlx 0.9.0（2026-05-06）的破坏点：MSRV 1.94（本机工具链 1.98，不挡）、`query*()` 改收 `impl SqlSafeStr`（非 `&'static str` 要包 `AssertSqlSafe`）、`Migrate` trait 改动、`RawSql` 加 `DB` 泛型。重点复核迁移、配对记录串行化、索引写入三处 0.9 破坏面。

## 后果

- `deny.toml` 不再有 RUSTSEC-2026-0459 忽略项，`cargo deny check advisories` 恢复成持续防线：以后新 advisory 直接红。
- 三处 crate 的 sqlx 查询与迁移代码按 0.9 破坏面适配。
- 验收（照卡 #1629）：`cargo deny check advisories` 通过且忽略项移除；`cargo nextest run -p storage -p core-index -p daemon` 全绿；反证——把 sqlx 退回 0.8 时 `cargo deny check advisories` 必须重新变红。

## 备选

- **只登记忽略项、继续用 0.8**：漏洞一直在，忽略项只压住告警，不解决任何东西。不取。
- **换 SQLite 驱动（如 rusqlite）**：改动面更大，sqlx 的 async 生态要整体重接，与本卡「修 CVE」的目标不成比例。不取。
