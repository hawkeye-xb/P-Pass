# 服务启停与自启纳入核心名单

## 背景

2026-11-09 Windows+iPhone 真机回归发现：用户在 Windows 上点「停止后台服务」后再点「启动后台服务」，服务起不来（#1582）。手机端随后一直连不上电脑、备份停摆。根因在 `crates/platform/src/windows.rs` 的 `install_autostart` 服务形态分支：只检查服务已安装就返回成功，没有真正执行启动。

这类文件当时不在 `.github/core-paths.txt`。现有口径是产品负责人 2026-11-03 定的五类（配对、加密、通信协议、数据存储与迁移、更新链）加点名卡；桌面端服务生命周期不在其中，因此按规则只能算「普通业务代码」，修复不需要方案拍板。

产品负责人在这次回归后指出：服务起不来就是 IPC 通道断、手机连不上、备份停摆，这比名单里不少条目更接近「用户能不能用」，应当算核心。

## 决定

在 `.github/core-paths.txt` 新增一节「服务启停与自启」，加入四个文件：

```
+ crates/platform/src/windows.rs
+ crates/platform/src/windows_service.rs
+ crates/platform/src/macos.rs
+ apps/desktop/src-tauri/src/service_state.rs
```

产品负责人 2026-11-09 拍板（#1585 评论）。

## 理由

**本质要保证什么**：服务在「该在的时候在」。这是备份可用性的前提——没有服务就没有 IPC 通道，手机连不上，备份停摆。它直接决定用户能不能用，后果比很多协议细节更严重。

**标准做法**：核心名单按「改错的后果」划定，而不是按模块边界。桌面端的服务生命周期（安装登记、启动、停止、自愈、更新时暂停与恢复）承担这个后果，应与人控的五类同级。

**偏离说明**：壳侧的大文件 `apps/desktop/src-tauri/src/lib.rs`、`distribution.rs` 也含服务启停逻辑，但没有整体纳入——文件太大，混有大量普通界面与更新逻辑，整体纳入会把日常改动都拖进人控。只纳入直接承载服务登记/启停的平台层与 `service_state`；若今后同类问题出在 `lib.rs`，再单独评估是否纳入。

## 后果

- 这四个文件的改动需要已采纳方案引用 + 带反证的测试（acceptance gate 判核心，评审同样）。
- #1582 的修复按人控流程：先出方案（两个选项 + 推荐）等拍板再改。
- `tools/test-ci-paths.sh` 增加四条断言（`core_is … true`），删掉或写错名单中的一行都会变红。

## 备选

- **只加 Windows 两个文件**：macOS 的 launchd 自愈同样承担「服务该在」的保证，且两平台要求一致（business-rules §8.3），只加一边会让同一类问题在 macOS 上仍然可以不经拍板改。
- **把 `lib.rs` / `distribution.rs` 整个加进名单**：范围过宽，把大量非服务逻辑也拉进人控，拖慢日常改动；本次只覆盖直接承载服务生命周期的文件。
