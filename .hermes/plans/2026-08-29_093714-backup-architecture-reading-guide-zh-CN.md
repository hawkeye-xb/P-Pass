# P-Pass 备份架构：中文阅读版（仅设计，未实施）

> 这份是手机阅读用的中文总稿。它只解释已经讨论出的架构方向、已经确认的产品语义，以及还必须拍板的核心问题；不代表任何代码已经改完。

## 一句话目标

备份不是“某个后台任务跑完了”。

> 一张被发现、且在用户备份范围内的照片，要么已得到电脑端的可靠确认，要么仍明确记录为待传、等待、重试、用户取消或永久失败；绝不能因为 App 被杀、网络变化、暂停或系统取消而悄悄消失。

## 已经确认的产品语义

### 1. 自动备份

```text
自动备份 = 系统自行决定何时备份

后台自动开启：App 在后台时也可自动发现、自动传输
后台自动关闭：App 在后台时不发现、不传输
前台打开 App：无论后台自动是否关闭，默认都可以自动备份
```

关闭后台自动备份不是删除待传照片，也不是用户暂停。

### 2. Pause、Continue、Cancel

```text
Pause
  用户要求当前备份管线不要自动继续

Continue
  恢复原来的未完成队列；不是重新全量扫描

Cancel
  用户明确放弃“本次传输”里尚未确认的内容；
  手机与电脑两侧都要清理活跃传输/staging 记录
```

### 3. 单文件永久异常

```text
文件不可读 / 被删除 / 协议明确拒绝 / 重试预算耗尽
  → 留下错误原因
  → 标为永久失败
  → 清理两侧活跃传输记录
  → 继续后面的正常文件
```

坏文件不能阻塞整批，也不能假装已经备份成功。

## 架构的核心分层

```text
界面层
  只显示状态、发送用户命令
      ↓
应用层
  统一的备份控制器：发现、传输、暂停、继续、取消、对账
      ↓
领域层
  纯业务规则：什么能传、哪个文件可重试、什么叫成功/取消/失败
      ↓
接口层
  业务需要的能力：状态库、媒体扫描、远端传输、调度、运行条件
      ↓
适配层
  Android MediaStore、Room/SQLite、WorkManager、JobScheduler、daemon 协议
```

### 这几件事必须彻底解耦

```text
MediaStore
  只回答：手机有什么本地媒体变化？

WorkManager / JobScheduler
  只回答：现在能不能/什么时候叫醒执行器？

远端 daemon / staging
  只回答：如何协商、传输、清理临时文件？

本地 BackupState 数据库
  唯一回答：哪些项已发现、待传、已确认、已取消、失败、待清理？
```

因此，不能再用 Work 名称、Work 状态、某个偏好布尔值或远端 staging 是否存在，来猜“用户是不是暂停了”或“文件是不是已完成”。

## 核心持久数据

```text
备份策略
  用户选了哪些相册、后台自动是否开启、自动备份条件、下次对账时间

发现游标
  本地相册变化已经可靠写入待传账本的位置
  不是“已经上传完成的位置”

传输意图
  一次可被 Pause / Continue / Cancel 控制的传输范围

传输项
  一个具体媒体版本：待传、占用中、等待重试、已确认、永久失败、用户取消

远端确认账
  远端何时确认拥有过哪个内容版本

清理待办
  用户取消或永久失败后，电脑端 staging 仍需清理时留下的可靠 outbox
```

最关键的事务：

```text
扫描到新照片
  → 同一数据库事务写入“待传项” + 推进“发现游标”

事务成功前崩溃：下次重扫，最多重复发现
事务成功后崩溃：待传项仍在，绝不丢照片
```

## 传输主线

```text
触发（Watch / 前台 / 周期 / 手动 / 对账）
        ↓
统一备份控制器
        ↓
检查：前后台、自动开关、范围、Wi‑Fi/电量、暂停状态
        ↓
扫描本地变化，原子写入待传项 + 游标
        ↓
从“最早可传”的待传项中取一个
        ↓
哈希、去重、传输、远端确认
        ├─ 成功：写已确认
        ├─ 暂时失败：只延后这一项，继续后项
        ├─ 永久失败：记录原因、清理 staging、继续后项
        └─ 系统停止：释放占用，回到待传；不等于暂停/失败
```

## 目前最需要先聊透的 P0 问题

### P0-1：什么时刻才叫“这张照片已经交付”？

当前协议是：

```text
开始批次 → 提交整批清单 → 上传缺失文件 → 整批提交
```

也就是说，当前确认边界是“整批提交”，不是“单文件确认”。

但我们想要的行为是：一张坏文件失败后，后面的继续传；每张成功的文件立刻可靠确认。

必须定：

```text
A. 第一版：每项单独走一次现有传输会话，先换正确性
B. 改协议：一个会话内支持逐项确认、逐项 abort，性能更好但工作更大
```

建议：领域模型按“每项确认”设计；第一版可先用 A，协议优化独立做，不让性能优化反过来污染业务语义。

### P0-2：Cancel 的“本次传输”到底是哪一组项？

连续队列天然没有“这一轮”的边界。必须选一种：

```text
A. 取消暂停时刻所属的一次传输快照      ← 推荐
B. 取消当前队列里所有未确认项
C. 以后由用户在 UI 中选具体项
```

没有这个答案，就不能定义 Cancel 的范围，也不能保证两侧 staging 清理正确。

### P0-3：Pause 时还要不要继续“发现”新照片？

```text
严格暂停（当前暂定）
  不扫描、不入队、不传输；Continue 后再扫描

仅暂停传输
  仍扫描并写入本地队列，但绝不联网传输
```

前者最符合“暂停备份就是停”；后者恢复更快、待传数更准确，但 Cancel 范围和用户预期更复杂。这个需要明确。

### P0-4：一个“媒体版本”怎样定义身份？

需要区分：

```text
同一张照片移动相册 / 改名       → 不应重复上传
同一条 MediaStore 记录内容被修改 → 应当成为新的待确认版本
不同文件内容 hash 相同          → 可远端去重，但文件级确认仍要准确
```

建议的候选身份：

```text
远端身份 + MediaStore 稳定引用 + 本地版本信息
（generation / 修改时间 / 大小）
```

哈希在真正读取后补上，用于远端去重和确认。

### P0-5：范围缩小、扩大、移动相册时怎么办？

必须写死：

```text
缩小范围：已入队但新范围外的项是否立刻取消并清理 staging？
扩大范围：水位以前的旧照片怎样被发现？
相册之间移动：是否根据当前范围重新裁决？
```

当前推荐：缩小范围立即终止范围外待传项；扩大或移动进范围时走“范围补发现”，不把全局发现游标倒退。

### P0-6：暂时失败与永久失败怎样裁决？

需要统一分类表，而不是每个 catch 自己猜：

```text
暂时：断网、超时、远端暂不可达、系统停止
永久：本地文件不存在/不可读、权限永久失效、协议明确拒绝
待定：磁盘满、配对失效、远端空间不足、hash 不一致
```

待定类必须决定：重试多久、何时需要用户处理、是否阻塞后项（默认不阻塞）。

## 讨论顺序建议

```text
先谈：P0-1 交付确认 + P0-2 Cancel 范围
再谈：P0-3 Pause 发现策略 + P0-4 媒体版本身份
然后：P0-5 范围变化 + P0-6 失败分类
最后：后台切换细节、对账周期、UI 文案与视觉表现
```

这些 P0 定下来以后，状态机、数据库 schema、传输协议和测试 case 才能一次成型；否则现在开始写代码，必然又会回到补丁式讨论。
