三星真机的 logcat 里，某天出现了这两行：

```
14:35:50  ActivityManager: Killing ...com.hawkeyexb.ppass (adj 915): one-time permission revoked
15:51:35  ActivityManager: Killing ...com.hawkeyexb.ppass (adj 900): one-time permission revoked
```

App 正在往家里电脑传照片，传到一半，进程没了。当天两次。

括号里的 adj 915 才是重点。安卓的后台回收天天在杀进程，这不算新闻；新闻是一个正在传文件的进程，在系统眼里已经被归到"随时可以死"那一档了。

## adj 这个数字值得先认识一下

oom_score_adj 是系统给每个进程打的"该先杀谁"分数，0 到 1000。个位数是前台，200 上下是前台服务能拿到的保护档，700 往上系统已经把你当闲着的，900 以上是纯缓存，内存一紧先走你。

900 到 915 这个区间说明：系统压根不知道这个进程在干活。那天"一次性权限到期"只是触发回收的导火索，只要进程停在这个档位，被杀只是时间问题。

搜"安卓后台被杀"能搜出一堆保活教程，这篇讲的不是那个。这个场景系统有官方答案，我们一直都有，只是后来把它弄丢了。

## 切到后台那一刻，保护就没了

两次被杀都是真实场景，先把它变成想复现就复现。往测试相册推 35 张 6MB 的图触发一次真实传输，传输进行中按 Home 切后台，每隔 10 秒读一次 `/proc/<pid>/oom_score_adj`：

```
t=0s          adj=700（刚切后台）
t=10s~60s     adj=700（传输还在跑，数字纹丝不动）
传完          adj=900
```

全程没有提升过。`dumpsys notification` 里，前台服务通知一条都没有。系统日志还有一行更直白的，三星省电框架打的：

```
SGM:FgCheckThread: pkgName: com.hawkeyexb.ppass is not in foreground
```

系统在反复确认这个进程是不是在前台干活，答案始终是否。顺带说一句，电池优化白名单管不了这件事。白名单只防 Doze 待机限流，不改 oom_adj，也不防内存压力下的缓存回收，它回答的是另一个问题。

## 13 天前的一次减负重构，把保护一起减掉了

翻提交历史，源头是 13 天前那次重构。负责传输的 Worker 当时 1147 行，传输逻辑已经搬进了新引擎，于是把它削到 125 行，只留一个纯粹的唤醒适配器。方向是对的，旧代码确实臃肿。

问题出在被删掉的东西里。旧 `doWork()` 开头有一行：

```kotlin
setForeground(foregroundInfo())
```

背后是一个 25 行的私有函数：建通知渠道、拼一条"正在备份照片"的常驻通知、包成 dataSync 类型的 ForegroundInfo。一行调用加函数本体，二十六行，干的是一件事：告诉系统"我在做用户能感知到的事，请按前台保护我"。

它长得像传输逻辑的一部分，实际回答的是另一个问题，"系统该不该保护我"。搬传输逻辑的人觉得它是 Worker 的事，删 Worker 的人觉得它是传输的事，两边都不认领，它就跟着瘦身一起没了。

更阴险的是 Manifest。`FOREGROUND_SERVICE_DATA_SYNC` 权限、dataSync 的服务声明，一行没删，全都在。事后翻 Manifest 审查"保护还在不在"，会得出齐全的结论。但声明只承诺"如果调用前台服务，我有权限"，调用本身没人负责。权限声明齐全，不等于保护真的存在。

## 把保护挂在一个不会有人"忘了调"的位置

最省事的修法是把这句调用塞回某个触发点，问题是下次重构它还会以同样的方式消失。所以这次不指望任何人记得，找结构兜底。

新架构里所有 Flow 触发动作最终都收口在一个统一收尾函数，前台服务的同步挂在那里：有传输在跑就 `startForeground`，没有就降级。要不要提升的判断写成一个独立的纯函数，输入复用账本里"这轮传输是否活跃"的既有事实，单测直接覆盖，决策和接线分离。

理由只有一句：保护性调用只要依赖调用方"记得调"，就一定会迎来下一次忘记。挂在必经之路上，人不在了它还在。

## 先反证一次，再上真机

先证明测试锁的是真机制：把收尾点里那句同步注释掉，接线测试当场真红，恢复即绿。改行为之前先确认测量本身有效。

真机复测，同样的 35 张图、同样切后台、每 8 秒采样：

```
全程 adj=200（前台服务档位）
```

`dumpsys activity services` 确认 `isForeground=true`、类型 dataSync。35 张全部确认送达，全程没有再出现杀进程记录。卡片的收尾状态留着"等真机长期回归观察"，这类系统行为的修复，验收标准不是某一次测试绿，是往后两周不复发。

这个修法也有明码标价的代价。前台服务要生效，通知栏就得常驻一条"正在备份"，用户躲不开，这是换系统保护交的官方税。还有一条三星真机上实测过的：通知权限没给的时候，`startForeground` 照样提升进程优先级，系统不因为通知不可见就拒绝保护，只是用户看不见那条提示条。保护归保护，可见性归可见性，两件事得分开验。

## 如果你也遇到传一半被杀

按这个顺序查，每一层都是一条命令：

1. 先看被杀时的 adj：`logcat` 里找 `ActivityManager: Killing`，或者 `cat /proc/<pid>/oom_score_adj`。700 以上，问题在 App 这边，不在厂商省电策略。
2. 再查前台服务是不是真的在跑：`adb shell dumpsys activity services <包名> | grep isForeground`。是 false 或者查无此服务，别看 Manifest，声明在不在跟跑没跑是两回事。
3. 白名单和忽略电池优化不解决问题，它们不改进程优先级。
4. 要减负重构了，对被删的每一行多问一句：除了看得见的业务职责，它有没有承担一个系统侧的隐藏职责。这类代码贴着业务逻辑写，最容易在瘦身时被整段带走。

这次我们的教训就是第 4 条本身。以后写保护性调用，挂流程必经的收口点，别指望下一个接手的人认得它。
