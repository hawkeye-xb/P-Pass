P-Pass 手机传照片给桌面这件事，中间有一步叫 `flow.fetch`：手机跟桌面说"我有一张照片要给你"，然后**在同一次网络请求里死等**，直到桌面把这张照片整个拉完、落盘、确认，才收到一句回音。

这个设计在同一个 Wi-Fi 下工作得很好。局域网延迟是毫秒级的，一张照片传完最多几秒，"等一下"感觉不出来。

它在跨网络、走中继（relay）的场景下会出一个很具体的问题：手机这边给这次等待设了 15 秒上限。传一张几百 KB 的截图，15 秒绰绰有余。传一个 224MB 的视频，走中继网络，光是这一次传输就可能要 80-90 秒。

于是手机会在第 15 秒准时判定"桌面没反应"，报错、退避重试，然后过一会儿再试一次——**同一个错误重复出现，用户能看见的现象就是"算完了，然后一直干等，最后传失败"**。

## 先看清楚：这不是"网络慢"，是设计上的自我矛盾

这个超时值同时要服务两个完全相反的目标：

- 如果桌面真的死了、断线了，我们希望**尽快**知道，好去重试或提醒用户；
- 如果传输是正常的，只是文件大、网络绕了远路，我们希望**耐心等下去**，不要在它明明进展正常的情况下把它判死。

一个数字不可能同时满足这两件事。调大它——正常的死连接判定要等更久；调小它——大文件必然被误杀。我们试过把这个数字从 15 秒挪到别的值，每次挪都是在两个错误之间选一个来承受，从来没有真正解决问题。这在项目里后来被明确写成一条规矩：*调数字是止血，不是终态方案*。

## 根因："提交任务"和"等结果"，本来就不该是一次网络请求

把问题往回退一步看：手机想做的其实是两件独立的事——

1. 告诉桌面"我要传这个"（提交）；
2. 知道桌面到底传完了没有（查询结果）。

这两件事被焊在了同一次 RPC 里，所以这次 RPC 的时长下限，被"传输本身要花多久"这个完全不可控的变量决定了。而"传输花多久"和"这次网络请求该不该超时"根本是两个维度的问题。

这个形状业界有一个标准答案，就是 HTTP 里熟知的 202 模式：提交一个任务，服务端立刻给你一个任务句柄，你后面拿着句柄去**查状态**，查状态这个动作本身永远是轻量、快速的，不管背后那个任务实际跑了多久。这套模式在这个项目里也不是第一次出现——桌面端的事件订阅早就是"推送做加速、轮询做兜底"的组合。这次要做的，是把同一个思路搬到手机传照片这条路径上。

## 改动：offer 立刻返回，status 负责查账

新的流程是三步：

```
手机: flow.offer（登记这次传输意图）  → 桌面立刻回应，不等传输
桌面: 后台把传输任务 spawn 出去异步跑，终态写进账本
手机: 隔一段时间 flow.status（查账本）→ active / completed / cancelled / failed / not_found
```

`flow.status` 是一次很轻的查询——它只读数据库和一个内存里的"任务是否还在跑"的标记，不碰真正搬运字节的那条数据面连接。所以不管这次传输实际要跑多久，`status` 请求本身永远能在正常的控制类超时（还是那个 15 秒，但现在它只管这一次轻查询）内返回。

这里有一条原则贯穿了整个实现：**手机只认账本，不认回声**。一次 `status` 查询本身超时了，不等于传输失败了——它只说明这次网络往返没成功，桌面账本上写的是什么状态，才是真相。下一轮再查一次账，如果账本仍是 active，就继续等，绝不因为一次查询超时就重新发一遍 `offer`、跟桌面正在跑的传输互相打架。

```kotlin
// NativeFlowDeliveryPort.kt（示意）
// 一次 status round-trip 失败 ≠ 传输失败；
// 只有账本明确写着 failed/cancelled，才是终态。
fun flowStatusPollOutcome(reply: FlowStatusReply?, consecutiveTimeouts: Int): PollOutcome
```

暂停和取消也借着这次机会分清楚了——之前"挂断连接"这一个动作同时兜着三层含义：租约还有效吗、任务还在跑吗、用户是不是不想要了。现在这三层各归各位：意图变化直接改账本状态，观察永远是"去查一次账"，没有任何环节靠"这通电话还接着吗"去猜。暂停留下的字节（partial）继续受保护，恢复时接着传；取消则真正放弃，partial 随后被垂圾回收清理——这是两条相反的账本路径，不能共用一套代码。

## 证明它是真的解决了，不是"看起来好了"

daemon 侧新增了一个测试，故意在数据面拉取里注入一段远超控制超时的延迟，断言手机侧的状态机必须靠轮询走到最终确认态、拿到回执——这个测试在改动前是真实失败的。

更硬的一个反证：临时把"记录当前任务，好让 suspend 能找到它去中断"这一行代码删掉重跑测试，`suspend` 变成了一个什么都没做的空操作，传输在后台悄悄跑完，测试断言的"必须收到明确的中断结果"直接失败。恢复那一行，测试立刻回绿。这证明测试锁住的是真实机制，不是摆设。

真机那一轮更直接：三星手机，全新配对，选中一个 224MB 的视频加 23 张照片，走同样的中继网络。视频那一项在桌面的账本状态从 active 走到 completed，花了大约 80-90 秒——远远超过旧代码里那条 15 秒线——全程没有一次失败或断连。这正是这条 15 秒超时线过去必然会误杀的场景。

## 还没做完的事

新机制没有把所有问题一次性解决干净，这里如实列出来：

- daemon 如果在传输过程中崩溃重启，目前 `status` 只会报告"任务不在跑了"，还不会主动重新拉起这次交付——这是设计里明确要求但还没实现的一块；
- 重复查询/重复拉取在最终确认态之后是否真的零重传字节，还差一个直接的断言测试；
- 一次拉取的最后一刻，如果用户正好在那个瞬间点了暂停或取消，两种时序谁赢——这条边界竞态还没补测试；
- 旧版本手机 + 新桌面、新版本手机 + 旧桌面 两个兼容方向，目前靠不破坏旧协议字段做保底，还没有专门的兼容性回归用例。

这次改动也顺带催生了一条写进团队协作规范的纪律：方案讨论时必须先说清楚"这是终态还是过渡"，止血可以先上，但不能没有同时开出对应的根治任务——这条超时数字前前后后被调过好几轮，每一轮都在两个错误之间摆钟，直到有人回头去看"这个数字到底在同时回答两个什么问题"，才算真正找到出口。
