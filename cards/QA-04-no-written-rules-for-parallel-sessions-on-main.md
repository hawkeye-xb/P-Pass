- **严重度猜测**：中高。今天没出事，但**全部依赖临场判断**：我遇到的五种情况

## 备注（挂号时已核实，供接卡人省一次考古）

**今天实际遇到的五种情况 + 我当时怎么处理的**（这就是草案的素材，全部有据）

| # | 情况 | 我的处理 | 如果换个做法会怎样 |
|---|---|---|---|
| 1 | push 被拒（远端已前进） | `git fetch` 看清对方改了什么，再 `git rebase`，历史保持线性 | `git pull` 默认 merge → main 长出交叉历史，二分变难 |
| 2 | 账本冲突（PROGRESS/QUEUE） | 手工留两边；**保留对方的排布不动**，只插自己那行 | 只留自己那边 → 静默吞掉别人的交付记录 |
| 3 | 撞到别人的红测 | 二分定位（只把那一个文件退回父提交）→ **测完原样还原** → 挂号 + 当场汇报，不改对方代码 | 顺手"修"别人的卡 → 两个会话同时改同一处；或装没看见 → 红留在 main |
| 4 | 要动共享文件 `tools/` | 先 `git log origin/main -5 -- tools/` 看对方在不在动同一批文件，选了不重叠的那个 | 直接改 → 真代码冲突，不是一行账本 |
| 5 | 自己的门禁会让 main 变红 | 断言与那 8 处修复**同一个提交**落地 | 分两次 → 中间那一刻 main 红，连带把别人的 ci-docs 搞红 |

**建议写进 `AGENTS.md` 的草案**（措辞待验收人定；本卡**不擅自改 AGENTS.md**）

1. **同步一律 `git fetch` + `git rebase`，不用 `git pull`。** 理由：main 要保持
   线性，二分才有用——今天 NET-26 就是靠单文件二分定位的。
2. **push 被拒不是错误，是常态。** 先 `git log main..origin/main` 看清对方改了
   什么再 rebase；对方动过的文件与自己重叠时，读一遍 diff 再继续。
3. **账本冲突手工解，两边都留，不动对方的排布。** `docs/PROGRESS.md` /
   `docs/QUEUE.md` 是每张卡必经之地，冲突是结构性的、不是谁的错。
   ⚠️ 不要给它们配自动合并（QA-03 已证伪：`merge=union` 的残留与正常历史
   不可区分）。
4. **撞到不是自己造成的红测**：二分定位 → 原样还原 → 挂号 + 当场汇报，
   **不改对方代码、不顺手"帮修"**。红线 5 的「红测不进 main」约束的是自己引入
   的红；别人已经在 main 上的红，处理方式是挂号和汇报。
5. **动共享文件（`tools/`、`justfile`、`.github/`、`AGENTS.md`）之前**，先看
   `git log origin/main -5 -- <路径>`。撞上了就换个时机或换个文件，别硬上。
6. **会让门禁变红的改动，必须与让它变绿的修复同一个提交。**
7. **开工前先看一眼别人在做什么**：`git log origin/main -10 --oneline` +
   `docs/QUEUE.md` 的状态列。这一条其实已经隐含在「开工按 session 类型分流」里，
   但没写明并行场景。

**接卡人注意**：以上第 3、6 两条与现有红线 5 有交集，措辞要一起看，别写成两套
口径。另外 `AGENTS.md` 开头就写着「一页化」，加这一节要控制篇幅——建议压成
一个小节 5–7 行，细则放本卡。


## 验收人拍板（2026-09-17）：改走分支 + PR

原话：「正常来说我们人之间协同不就是提 PR，往分支里面合，有人去 review 就好了，
对吧？这样的话往前进了多少都跟我们这一轮的任务没有关系，而不是说我们修改同一个
分支。我们用标准的多人协同流程去规范开始任务和提交代码这个过程。」

**所以上面那份「把直推 main 的临场判断写成规则」的草案作废**（保留原文供追溯，
它记录的五种情况仍然是真实发生过的素材）。方向改为标准 PR 流。

### 已核实的事实（接卡人别再查一遍）

- ✅ **CI 零改动**：`ci-rust` / `ci-android` / `ci-desktop` / `ci-docs` 四条 lane
  的 `on:` 里**都已经有 `pull_request`**（外加 `push`）。开 PR 就会跑，
  且 paths 过滤照旧生效（纯文档 PR 只点起 ci-docs）。
- ❌ **仓里没有 PR 模板、没有 CONTRIBUTING**（`.github/` 下只有
  `dependabot.yml` + `workflows/`）。
- ✅ 分支推送可用（远端已有 `dependabot/*`、`archive/rules-v1-2026-09-16`）。
- 🔴 **硬约束：agent 开不了 PR、也合不了 PR。** 本机 `gh` 绑的是公司账号、本仓
  不许用（见 `AGENTS.md` 交付段 + 个人/公司隔离规则）；而「凭据只在 GitHub
  Secrets」这条红线又禁止在开发机上装 token。**所以「开 PR」和「合 PR」这两步
  必然落在验收人手上（网页操作）。** 这是这套流程在本仓的固定成本，不是可以
  优化掉的环节——接卡人不要试图用脚本绕过它。

### 必须一起决定的三件事（本卡不替验收人决定）

1. **合并方式**：建议 **squash merge**。main 保持一卡一提交、线性——今天
   NET-26 就是靠单文件二分定位的，历史一交叉这个能力就废了。
2. **分支保护要不要开 "require branches to be up to date before merging"**：
   **建议开**。理由是今天的真实案例：我能发现并行会话把
   `suspend_interrupts_...` 弄红（NET-26），**正是因为 rebase 到最新 main 之后
   跑了 CI**。纯分支模式下 PR CI 只测自己那一份，这个红要等合并后才暴露。
   这条设置正好把「合并前必须与最新 main 一起绿一次」变成机器强制。
   代价：main 动得快时需要多 rebase 几次。
3. **账本那一行怎么处理**：**分支不解决账本冲突，只是把它推迟并集中**。今天
   全部冲突都在 `docs/PROGRESS.md` / `docs/QUEUE.md`——每张卡必经之地。分支活
   得越久分歧越大。两个选项：⒜ 接受合并时解冲突（与今天一样，只是换了时机）；
   ⒝ 账本那一行留到 PR 即将合并前最后一刻再加。**⒝ 更省事但会让 PR 在 review
   阶段看不到账本改动**，需要权衡。

### 建议的流程骨架（措辞待定，接卡人写进 `AGENTS.md` 并压到一页内）

    开工：git fetch origin && git switch -c <type>/<卡号>-<slug> origin/main
          type ∈ {feat, fix, docs, test, ci}
    干活：先改卡 → 再改代码 → 同批提交（现有纪律不变）
    自验：动了代码跑 just ci；纯文档跑 just ci-docs（QA-03 新增）
    交付：git push -u origin <分支>  →  **停在这里，汇报分支名 + 自验结果**
          开 PR / review / 合并由验收人在网页完成
    红测：留在自己分支上，不进 main——红线 5 的 wip/<卡号> 可以被本流程取代，
          因为分支本身就是隔离；措辞要一起改，别留两套口径

### 范围

- 只准动：`AGENTS.md`（加一节并删掉与之矛盾的旧措辞）、
  `.github/PULL_REQUEST_TEMPLATE.md`（新建，可选）、本卡与 QUEUE/PROGRESS。
- 不准动：`.github/workflows/**`（已支持 `pull_request`，不需要改）、
  任何业务代码。
- ⚠️ 分支保护与合并方式是 **GitHub 仓库设置**，在网页上改，不在仓里——
  接卡人只负责把决定写进文档，不要试图用代码实现它。


## 更正记录（2026-09-17，验收人指出后当天更正）

本卡上一版把两件事说重了，验收人两句话就点破了：

**① 「agent 开不了 PR」不是硬约束。** 我写成"固定成本、不可优化"，还叮嘱接卡人
别去绕——错了。GitHub 支持**预填链接**：

    https://github.com/hawkeye-xb/P-Pass/compare/main...<分支>?expand=1&title=<urlencode>&body=<urlencode>

agent 推完分支给出这条链接，验收人点开时标题与正文已经填好，只需按「Create」。
`gh` 不可用完全不影响这套流程——它挡的只是"agent 自己合并"，而合并本来就该是人做。
**教训：把一个自己没查过的限制写成"不可优化"，比漏掉它更糟**，它会让接卡人
也不去找办法。

**② CI 不需要任何改动，现状就已经是验收人要的形状。** 我以为要把 `push` 触发
限定到 main，查完发现四条 lane 的 `push:` 里**本来就写着 `branches: [main]`**。
所以：

    推分支              → 零 CI（push 只盯 main）
    开 PR               → 跑受影响域的 pull_request lane（paths 过滤照旧）
    合入 main           → 再跑一次 push lane

正是验收人说的"分支开发时快速验证，开 PR 时再跑 CI/CD"。**一行 yml 都不用动。**

### 本次实际落地

- `AGENTS.md` 交付段首条改成「一卡一分支、走 PR、不直推 main」，含分支命名、
  停在 push 后、预填链接格式。
- `AGENTS.md` 加「分支上快验，PR 上全验」，写明推分支零 CI 的事实依据。
- `AGENTS.md` 红线 5 口径统一：`wip/<卡号>` 那套删掉——一卡一分支本身就是隔离，
  红测就留在自己分支上别开 PR（或标 draft）。
- 新增 `.github/PULL_REQUEST_TEMPLATE.md`：卡 / 改了什么 / 自验（含反证与 E 级）/
  账本 / 留白挂号。
- `.github/workflows/**` **一个字没动**（见更正②）。

### 仍然只有验收人能定的三件（GitHub 仓库设置，不在仓里）

1. 合并方式建议 **squash**——main 一卡一提交、线性，单文件二分才有用（NET-26 靠它定位）。
2. 分支保护 **require branches to be up to date before merging** 建议开——
   今天能发现并行会话把 `suspend_interrupts_...` 弄红，正是因为 rebase 到最新
   main 后跑了 CI；纯分支模式下 PR CI 只测自己那份。开了它等于机器强制"合并前
   与最新 main 一起绿一次"。
3. 账本那一行的时机：分支不消除 `PROGRESS.md`/`QUEUE.md` 的冲突，只是推迟并集中。
   合并时解（同今天）或留到临合并前再加，各有代价。
