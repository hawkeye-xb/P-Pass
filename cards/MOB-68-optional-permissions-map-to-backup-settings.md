# MOB-68 可选授权绑定到后台备份和失败通知（L2）

> 🟡 状态：授权流程与后台备份开关已真机回归通过（2026-09-10）；等待将
> `work/MOB-68-permission-settings` 合入 main。失败通知发送不属本卡，见 MOB-67。
> 级别：**L2** · 阻塞：无 · 协同分支：`work/MOB-68-permission-settings`

## 问题

首装时，「备份范围」所需的媒体权限与两个可选能力混在全局提示/弹窗体系中：
电池白名单和通知权限会占用跨 tab 黄条，用户看不到它们分别控制什么；多个
App 对话框又可与系统授权流程重叠。设置页的「自动备份」在备份规则外独立摆放，
且不能明确作为重新申请电池白名单的入口。

「备份失败时通知我」的**通知权限申请**纳入本卡；真实失败事件是否发送系统通知
是独立的 MOB-67，不在本卡实施范围内。

## 期望行为

### 首装流程

1. 配对成功后进入「备份范围」；这是必需能力，先申请媒体权限并完成相册选择。
2. 仅在范围已完成后，才依次提供可跳过的「后台备份」和「备份失败时通知我」。
   不批量索权；一个系统授权未返回前，不显示另一个 App 对话框或系统授权。

### 一对一设置映射

- **后台备份**：替代现有「自动备份」，移入备份设置。开启时若未在电池白名单，
  发起系统白名单请求；批准才启用自动后台 producer，拒绝/撤销时显示为未开启，
  用户可再次点开重试。关闭只禁止未来自动触发，不暂停或取消当前 Flow 轮次。
- **备份失败时通知我**：位置和文案不改。用户打开时才申请通知权限；拒绝/撤销时
  开关不可假装开启。真实失败通知的发送见 MOB-67。
- 电池白名单与通知权限不再作为 `NoticeHost` 的全局授权黄条；授权状态只在其
  对应设置项和 onboarding 步骤中呈现。

## 已定产品语义

- 媒体权限是备份范围的必要前提；电池白名单和通知权限都是可选能力，必须在范围
  完成后按用户对对应功能的明确操作申请。
- 「后台备份」是 UI 名称；系统白名单授权是独立的 OS 事实，App 每次回前台重新读取，
  不以本地偏好伪造授权已存在。
- 本卡只解决授权流程与两项设置的行为；授权流程结束后，才单独盘点其余现有弹窗。

## 实施记录

- 设置入口：后台备份移入「备份」规则并改名；未在白名单时开启会走系统白名单请求，
  批准后才启用自动 producer。失败通知开关仅在用户打开时请求通知权限，拒绝不保留
  虚假的开启态。
- 呈现：`NoticeHost` 不再构造电池白名单或通知权限候选。
- onboarding：首次选完相册只保存范围；点「进入 App」后才先自动请求电池白名单，
  系统框返回后才自动请求通知权限，二者结束后才 discovery/传输。该过程内更新弹窗
  延后，不与系统授权叠加。
- 真机：验收人已在完整卸载重装后的首装流程回归确认授权顺序与传输时机正确
  （2026-09-10）。
- 真机：后台备份开时，后台新截图可同步；关闭后同一场景在一段时间内不触发。
  重新打开 App 后由前台路径补传，符合「关闭仅禁止后台自动触发、不丢待备份照片」
  的产品语义（2026-09-10）。
- 真实失败未收到系统通知的真机证据已移交 MOB-67；通知权限本身不再是该问题的
  阻塞点（2026-09-10）。

  Gradle 输出 `BUILD SUCCESSFUL`，25 actionable tasks。
